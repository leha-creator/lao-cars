# Уведомления сотрудникам

Как сотрудник узнаёт о новой заявке: три канала доставки, кто и куда получает сообщение, что настроить перед запуском и как разобраться, почему уведомление не пришло.

Правило раздела то же, что и в [«Заявках»](leads.md): **заявка первична, уведомление вторично.** Любой канал может лежать — заявка всё равно в базе и видна в панели. Ни один отказ доставки не влияет ни на ответ формы, ни на сохранение лида.

## Три канала

| Канал | Что это | Есть ли персональные данные клиента |
| :---- | :---- | :---- |
| Telegram | Личное сообщение от бота с полным содержанием заявки | Да — приватный чат |
| Push в браузере | Всплывающее уведомление системы на подписанных устройствах | **Нет** — только источник и имя |
| Колокольчик в панели | Значок с числом непрочитанных, опрос раз в 30 секунд | Да — панель за авторизацией |

**Телефона и комментария в push нет намеренно.** Push рисует система поверх экрана блокировки — то есть на экране, который видит не только адресат: разбуженный телефон лежит на столе в мастерской. Всё остальное открывается по клику, уже в карточке заявки за авторизацией. Добавить телефон «чтобы менеджер сразу перезванивал» выглядит очевидным улучшением и стоит ровно того, ради чего в проекте вообще заведён запрет на персональные данные в логах: вычистить их оттуда, куда они однажды попали, нельзя.

## Кто получает заявку

Получателей выбирает один сервис — `LeadNotifier`. Больше о составе адресатов не знает никто.

| Канал | Условие получения |
| :---- | :---- |
| Telegram | `Уведомления в Telegram` включены **и** заполнен `Telegram chat ID` |
| Push и колокольчик | `Уведомления в браузере` включены |

Оба флага по умолчанию включены: сотрудник, заведённый до появления настроек, не должен молча остаться без уведомлений. Фактическую доставку при этом всё равно ограничивают заполненный адрес и наличие подписки браузера.

**Push и колокольчик — один флаг, но не одно и то же.** Колокольчик работает всегда, когда флаг включён: ему не нужны ни ключи VAPID, ни разрешение браузера. Push поверх него требует и того, и другого. Поэтому сотрудник с включённым флагом и без разрешения браузера продолжает видеть заявки в панели — просто без всплывающих окон.

**На каждого получателя ставится своя задача.** Это не деталь реализации, а причина, по которой раздел устроен именно так: цикл по списку получателей внутри одной задачи упал бы на пятом и увёл бы в ретрай всю задачу — первые четверо получили бы заявку повторно. И тем чаще, чем хуже работает связь.

### Общий чат Telegram — фолбэк

`TELEGRAM_MANAGER_CHAT_ID` из окружения остаётся в проекте, но обращаются к нему, **только когда персональных получателей нет вовсе**. Как только первый сотрудник заполнил свой `chat ID`, общий чат замолкает.

Оба «очевидных» варианта отклонены:

- слать и в общий, и в персональные — это дубль каждой заявки навсегда, начиная с первого заполненного профиля;
- убрать общий совсем — это молчание в промежутке между запуском и тем днём, когда сотрудники заполнят профили. То есть ровно тот отказ, который в проекте назван самым дорогим: сайт снаружи выглядит работающим, а о заявках никто не узнаёт.

Срабатывание фолбэка пишется в лог с пометкой `fallback`. День, когда эта пометка исчезнет из записей, — это день, когда общий чат перестал получать заявки, и объяснить его иначе будет нечем.

## Настройка сотрудником

Всё живёт на странице **профиля** в панели (значок пользователя справа вверху → «Профиль»), в секции **«Уведомления»**.

**Telegram.** Включить переключатель и вписать свой `chat ID` — узнать его можно у бота [@userinfobot](https://t.me/userinfobot). Только цифры; у групповых чатов id отрицательный, поэтому ведущий минус допускается. Пока поле пустое, уведомления в Telegram не приходят, даже если переключатель включён.

**Браузер.** Включить переключатель и нажать **«Разрешить уведомления в этом браузере»**. Разрешение спрашивает браузер, и спрашивает он его один раз: нажатие «Блокировать» отзывается только в настройках самого браузера, поэтому страница ничего не запрашивает сама и ждёт нажатия кнопки.

Ниже — список подписанных устройств: браузер, система, дата подписки и когда на него последний раз уходило уведомление. Кнопка «Отозвать» удаляет подписку конкретного устройства.

Блок различает четыре состояния, и четвёртое — главное:

| Что видно | Что это значит |
| :---- | :---- |
| Кнопка «Разрешить уведомления» | Разрешение ещё не запрашивали |
| «Этот браузер подписан» | Всё работает |
| Объяснение про настройки браузера | Разрешение запрещено — снимается только в самом браузере |
| Снова кнопка «Разрешить» при выданном разрешении | Подписки нет: браузер переустановлен или очищены данные сайта |

Последнее состояние выглядит как «не подписан» намеренно. Показать его как «всё в порядке» значит оставить человека ждать уведомлений, которых не будет.

**Подписка принадлежит учётной записи, а не браузеру.** Рабочий компьютер, ноутбук и телефон — три подписки на одного сотрудника. И наоборот: если за одним браузером вошёл другой сотрудник, подписка переезжает к нему — иначе заявки уходили бы не тому.

## Запуск на проде

Три обязательных шага. Незаполненные ключи не роняют ничего: push просто пропускаются с записью WARN в лог — ровно как несконфигурированный Telegram. Симптом при этом тот же, что и у забытого токена бота: сайт снаружи работает, сотрудник уведомлений не получает.

**1. Сгенерировать пару ключей VAPID** — один раз за жизнь проекта:

```bash
php artisan webpush:vapid          # записать пару прямо в .env
php artisan webpush:vapid --show   # только показать, ничего не записывая
```

Первая форма дописывает `VAPID_PUBLIC_KEY` и `VAPID_PRIVATE_KEY` в `.env`; если ключи там уже есть, команда спросит подтверждение, а в production потребует `--force`. Вторая форма ничего не трогает и просто печатает пару — она нужна там, где переменные задаются не файлом, а окружением контейнера.

Дополнительно стоит задать `VAPID_SUBJECT` — контакт для push-сервиса на случай проблем с доставкой (`mailto:admin@example.com` или адрес сайта); пустой заменяется на URL приложения.

> **Ключи не меняются никогда.** Новая пара делает мёртвыми все существующие подписки разом, а сотрудник об этом не узнает: кнопка в кабинете по-прежнему покажет «этот браузер подписан». Ключи из `.env` обязаны переживать деплой и попадать в бэкап конфигурации.

**2. Проверить HTTPS.** Push не работают по `http://` нигде, кроме `localhost`. Стейджинг без сертификата — самая частая ловушка: локально всё работает, на стенде кнопка «ничего не делает». Страница объясняет это текстом, но лучше не доводить.

**3. Убедиться, что `public/sw.js` отдаётся с корня сайта.** Service worker обязан быть доступен по адресу `/sw.js`: область видимости worker'а равна каталогу, из которого он отдан, а уведомления ведут в `/admin/...`. Никаких переписываний пути в конфиге веб-сервера.

**Про расширение `gmp`.** Оно **не обязательно**: `minishlink/web-push` объявляет его как рекомендацию, а не требование, и без него длинная арифметика подписи уходит в `bcmath` или в чистый PHP. В прод-образе его стоит иметь ради скорости эллиптической подписи — но собранный без него образ работает.

Service worker **ничего не кеширует** и делать этого не должен. Кеширующий worker переживает деплой и продолжает отдавать старые ассеты при новом манифесте Vite; симптом — «сайт сломался у одного человека и чинится только жёстким сбросом» — не воспроизводится больше ни у кого, включая того, кто будет его искать.

## Диагностика

Все события уведомлений идут в тот же файл, что и заявки, — `storage/logs/leads.log` (ротация 30 дней).

| Запись | Уровень | Значит |
| :---- | :---- | :---- |
| `уведомления поставлены в очередь` | INFO | Задачи ушли в Redis. В контексте — число получателей по каждому каналу и признак `fallback` |
| `получателей уведомлений нет ни по одному каналу` | WARN | **Заявка сохранена, но о ней никто не узнает.** Ни одного сотрудника с включёнными уведомлениями и пустой общий чат |
| `уведомление доставлено в Telegram` | INFO | Сообщение ушло. `chat_id_tail` — последние 4 знака адреса |
| `уведомление менеджеру не доставлено` | ERROR | Пять попыток Telegram исчерпаны |
| `ключи VAPID не заданы, push пропущены` | WARN | Push пропущены целиком. Одна запись на заявку, а не на получателя |
| `уведомление доставлено` (push) | INFO | Push принят push-сервисом браузера |
| `протухшая подписка удалена` | INFO | Push-сервис ответил 404 или 410: браузер переустановлен или разрешение отозвано. Строка удалена автоматически |
| `уведомление не доставлено` (push) | ERROR | Настоящий отказ доставки: недоступный push-сервис, неверная подпись, слишком большая полезная нагрузка |
| `подписка создана` / `подписка обновлена` | DEBUG | Браузер зарегистрировал подписку |
| `подписка отозвана` | DEBUG | В контексте `origin`: `browser` — из браузера, `profile` — кнопкой в кабинете |
| `настройки уведомлений изменены` | INFO | Сотрудник поменял флаги. `chat_id` целиком не пишется — только признак «заполнен / очищен» |

Ни в одной записи нет ни персональных данных клиента, ни полного `endpoint` подписки, ни полного `chat_id` сотрудника, ни ключей шифрования: `endpoint` — это адрес доставки конкретному человеку, а лог живёт 30 дней и уезжает в бэкапы.

```bash
# Что происходило с уведомлениями сегодня
tail -f storage/logs/leads-$(date +%F).log

# Кто вообще числится получателем
php artisan tinker --execute="dump(App\Models\User::receivingPush()->count(), App\Models\User::receivingTelegram()->count());"
```

### Типичные ситуации

| Симптом | Причина | Что делать |
| :---- | :---- | :---- |
| В логе WARN «получателей нет ни по одному каналу» | Никто не включил уведомления, общий чат пуст | Заполнить профили сотрудников или задать `TELEGRAM_MANAGER_CHAT_ID` |
| Заявки в панели есть, push не приходят, в логе WARN про VAPID | Ключи не сгенерированы | `php artisan webpush:vapid`, затем `php artisan config:clear` |
| Кнопка «Разрешить уведомления» ничего не делает | Страница открыта по `http://` | Поставить сертификат; на `localhost` это исключение и работает |
| В кабинете «этот браузер подписан», push не приходят | Разрешение отозвано в системе, а не в браузере | Проверить настройки уведомлений ОС для браузера |
| Устройство пропало из списка само | Push-сервис ответил 404/410, подписка удалена | В логе — INFO «протухшая подписка удалена». Подписаться заново |
| Один сотрудник получает заявки дважды | Заполнены и персональный, и общий чат у одного человека | Общий чат — фолбэк; проверить, что персональный `chat ID` не совпадает с `TELEGRAM_MANAGER_CHAT_ID` |
| Колокольчик пуст, хотя заявки есть | Заявки пришли до включения флага | Уведомления не рассылаются задним числом |
