# Заявки и уведомления

Как заявка проходит путь от формы на сайте до записи в базе, что настроить перед запуском, как понять, что что-то сломалось, и как менеджер работает с заявкой в панели.

Кому и по каким каналам уходит сообщение о заявке — отдельная страница: [«Уведомления сотрудникам»](notifications.md).

Главное правило раздела: **заявка первична, уведомление вторично.** Канал доставки недоступен — заявка всё равно в базе и видна в панели. Обратное неверно: потерянная заявка не восстанавливается ниоткуда.

## Путь заявки

```
Форма на странице
      │  POST /leads  (CSRF + throttle:leads)
      ▼
StoreLeadRequest ──► honeypot заполнен? ──► да ──► ответ «Заявка принята», в БД ничего
      │ нет
      ▼
  валидация ──► ошибки ──► сообщения на форме, введённое сохранено
      │ ок
      ▼
LeadService::capture()
      │  DB::transaction: запись в `leads`
      │  INFO в канал `leads`
      ▼
LeadNotifier::notify()  ──► кому и по каким каналам
      │
      ├─► NewLeadNotification ──► очередь ──► push + колокольчик панели
      └─► NotifyManagerAboutLead ──► очередь ──► Telegram (своя задача на получателя)
```

Ответ пользователю формируется сразу после записи в базу — до того, как кто-либо обратился к внешним сервисам. Форма не ждёт ни Telegram, ни push-сервис браузера.

## Два формата ответа

Форма отправляется **без перезагрузки страницы**, но остаётся обычной POST-формой: `action`, `method`, `@csrf` и кнопка `type="submit"` в разметке на месте, а `fetch` лежит поверх и висит на `submit.prevent`. При неработающем `app.js` форма отправляется браузером и получает прежний редирект с баннером над ней. Так же устроены фильтры каталога и фотогалерея — форма заявки не исключение, а тот случай, где деградация важнее всего.

**Формат ответа выбирает сервер по заголовкам запроса** (`Accept: application/json`), а не по полю формы. Скрытое поле вида `ajax=1` дало бы ту же функциональность и сделало бы контракт ответа зависимым от разметки — которую как раз и правят.

| Ситуация | Без JavaScript | Через `fetch` |
| :---- | :---- | :---- |
| Заявка принята | Редирект назад, баннер `session('status')` | `200` + `{"message": …}`, модальное окно «Заявка принята» |
| Honeypot заполнен | **То же самое**, лид не создан | **То же самое**, лид не создан |
| Ошибка валидации | Редирект с сообщениями под полями | `422` + `{"errors": {"phone": […]}}`, сообщения под полями |
| Лимит по IP исчерпан | Редирект с ошибкой под полем «Телефон» | `429` **в формате ошибок валидации** + `Retry-After` |
| Сессия устарела | Штатная страница 419 | Сообщение «обновите страницу и отправьте форму заново» |
| Сеть недоступна | — | Сообщение над кнопкой с предложением позвонить |

Три строки этой таблицы держат раздел:

- **honeypot отвечает успехом в обоих форматах.** JSON-ветка, которая про него забыла, называет боту имя поля-ловушки кодом ответа, и ловушка перестаёт работать после первого прогона;
- **лимит отвечает `429` с телом в формате ошибок валидации.** Клиент разбирает `422` и `429` одной веткой и рисует текст под полем «Телефон». Голый `429` вернул бы человека за общим адресом к странице ошибки — то, ради чего лимит и отвечает редиректом на пути без скрипта;
- **сообщения об ошибках у формы два комплекта, и это не дубль.** Серверный (`@error`) печатается только после редиректа, клиентский — только при живом `fetch`; одновременно они появиться не могут, а первый клиентский сабмит гасит серверные, если скрипт догрузился на странице с ними.

Модальное окно подтверждения живёт в layout **ровно одно на страницу** и связано с формой событием: форма встречается на странице дважды (карточка автомобиля плюс секция заявки), а окно обязано быть одно — как и якорь `#lead-form`.

## Формы и поля

Все формы сайта — один Blade-компонент `x-lead-form` (сам `<form>`), обёрнутый в `x-lead-section` там, где нужна секция с заголовком и фоном. Различаются они источником и одним флагом:

| Где | Как монтируется | Источник в списке заявок |
| :---- | :---- | :---- |
| Карточка автомобиля | `<x-lead-form :source="$car" title="…" />` внутри своей карточки | `Авто: Zeekr 001` |
| Главная, контакты, автосервис | `<x-lead-section title="…" />` | `Общая форма` |
| Запчасти | `<x-lead-section :parts="true" title="…" />` | `Общая форма` + поля автомобиля |
| Конкретная услуга (веха 4.4) | `<x-lead-section :source="$service" title="…" />` | `Услуга: Полировка кузова` |

Все четыре сценария смонтированы и работают. На странице автосервиса и на главной форма получает список позиций прайса (`:services`), и клик по строке подставляет позицию в селект «Интересует»; без JavaScript клик доводит до формы, где позиция выбирается вручную.

Вёрстка формы — веха 4.1, по UI Kit макета; вехой 4.3 из неё вынесена секция-обёртка, вехой 4.7 поверх лёг `fetch`, но содержимое `<form>` не изменилось ни в одном инварианте. Правится в ней **только разметка**: honeypot за пределами экрана, отсутствие скрытого `page_url`, `old()` во всех полях, `maxlength="17"` на VIN и кнопка `type="submit"` — каждый инвариант с объясняющим комментарием в шаблоне. Если после правки формы пришлось менять `LeadStoreTest` — сломано поведение, а не разметка.

Поля формы:

| Поле | Обязательное | Ограничение | Примечание |
| :---- | :---- | :---- | :---- |
| Имя | да | 120 символов | |
| Телефон | да | 32 символа | Проверяется маской `+?[0-9 -()]{10,20}` |
| E-mail | нет | 255 символов | |
| Комментарий | нет | 2000 символов | |
| Способ связи | нет | телефон / WhatsApp / Telegram | |
| Удобное время | нет | утро / день / вечер | |
| Марка, модель, VIN | нет | VIN — 17 символов | Только при `:parts="true"` |
| Согласие на обработку ПДн | **да** | правило `accepted` | Чекбокс, веха 4.17 — см. раздел ниже |

Ограничения длины совпадают с колонками таблицы. Ослабить правило ниже длины колонки нельзя: тогда вместо сообщения на форме придёт ошибка драйвера PostgreSQL, и заявка потеряется.

**Адрес страницы в заявку кладёт сервер**, а не скрытое поле формы. Значение уходит ссылкой в уведомление менеджеру, и клиентское поле превратило бы уведомление в вектор фишинга. Берётся адрес предыдущей страницы из сессии, проверяется на принадлежность своему хосту (`APP_URL`) и обрезается до 255 символов.

**Заявка на подбор запчасти отличается не источником, а полями автомобиля клиента** — этого автомобиля в каталоге нет.

## Согласие на обработку персональных данных (веха 4.17)

Форма не принимается без отмеченного чекбокса: правило `accepted`, то есть отсутствующее поле — тоже отказ. Это существенно, потому что именно так приходит неотмеченный чекбокс: браузер не кладёт его в запрос вовсе, и `new FormData(form)` в `lead-form.js` ведёт себя так же. **Клиентского кода согласие не потребовало** — существующий разбор ошибок раскладывает `consent` по контейнерам сам.

Факт согласия пишется в две колонки `leads`:

| Колонка | Что значит |
| :---- | :---- |
| `consented_at` | Момент согласия. `null` — согласие через форму сайта не давалось |
| `consent_policy_version` | Редакция политики, действовавшая в этот момент |

**Обе nullable, и это не мягкость.** `null` означает ровно одно и означает честно: заявки, заведённые до вехи, и всё, что придёт из консоли или импорта. `NOT NULL` с умолчанием `now()` проставил бы старым строкам согласие, которого никто не давал.

`consented_at` заведён **отдельно от `created_at`**, хотя для веб-заявки значения совпадут до секунды: `created_at` отвечает на вопрос «когда появилась строка», `consented_at` — «когда человек согласился». Считать согласие по `created_at` значит утверждать, что каждая строка в таблице получена с согласием.

**Штамп ставит `StoreLeadRequest::toData()`, а не `LeadService::capture()`** — по той же причине, по которой там же определяется `page_url`: запрос это единственное место, которое ЗНАЕТ, что чекбокс был отмечен. `capture()` зовётся ещё из теста, консольной команды и будущего импорта.

Редакция берётся из настройки политики. **Очищенная редакция заявку не отклоняет:** отказать человеку из-за пустого поля в админке — худшее из решений, доказательством согласия остаётся `consented_at`, а пустое поле видно и в карточке заявки, и в записи канала `leads`. Предупреждение об этом пишется при сохранении настроек, а не на каждую заявку: поток одинаковых WARNING перестают читать через час.

В разметке чекбокс связан с подписью через `id`/`for`, а **не обёрнут в `<label>`**, как остальные поля: внутри подписи стоит ссылка на политику, и клик по ней внутри `<label>` переключал бы согласие. Идентификатор генерируется на каждый рендер — форм на странице может быть две (карточка автомобиля плюс секция заявки), и константный `id` дал бы клик по подписи второй формы, переключающий чекбокс первой.

Сам документ — редактируемый из панели текст, публичная страница `/privacy`. Что там правится и когда — в [«Справке в панели»](help-center.md), статья «Персональные данные и приём заявок».

## Выключатель приёма заявок (веха 4.17)

Уведомление об обработке персональных данных подаётся в Роскомнадзор **до начала обработки**, а обработка начинается с первой принятой заявки. Поэтому приём заявок выключается настройкой `legal.forms_enabled` — тумблер «Приём заявок» на вкладке «Персональные данные».

**Умолчание при отсутствующей настройке — «выключено».** Нет строки настройки (а на проде её не будет до `laocars:install-legal-settings`) — приёма нет. Обратный выбор отказывал бы в безопасную сторону только пока строка на месте, то есть вёл бы себя неправильно ровно в тот момент, ради которого выключатель и сделан.

Выключение работает **в двух слоях**, и второй обязателен:

| Слой | Что делает |
| :---- | :---- |
| Разметка (`x-lead-form`) | Вместо `<form>` — блок «приём приостановлен» и телефон компании ссылкой `tel:` |
| Сервер (`StoreLeadRequest::authorize()`) | 403 на `POST /leads`, запись в базу не создаётся |

Без серверного слоя роут остаётся публичным независимо от того, что нарисовано на странице: заявка придёт с закешированной страницы, из вчерашней вкладки, от бота или из curl — и будет принята. Спрятать форму в разметке это оформление, а не запрет.

**Секция заявки при этом со страницы не исчезает.** Кнопка «Оставить заявку» в шапке ведёт на `#lead-form` на КАЖДОЙ странице сайта; туда же ведут строки прайса, карточка «Поддержка» на главной и умолчание `home.promo.link_url`. Убрать секцию вместе с формой значит сделать мёртвыми кнопку в шапке и три ссылки разом — на страницах, которых правка не касалась. Меняется содержимое карточки, а не наличие секции; на инвариант стоит отдельный сторож.

Развилка живёт **в компоненте `x-lead-form`**, а не на местах вызова: вызовов шесть, и забытый означал бы живую форму при выключенном приёме.

Ответ `403` на пути `fetch` попадает в общую ветку разбора `lead-form.js` и показывает запасное сообщение про соединение. Формально неточно, фактически безвредно: при выключенном приёме формы на странице нет вовсе, и этот ответ видит только тот, у кого открыта устаревшая вкладка.

Тесты, отправляющие форму, обязаны включать приём явно — помощник `enableLeadForms()` в `tests/Pest.php`, вызывается в `beforeEach` восьми файлов. Глобально он не поставлен намеренно: тогда состояние «приём выключен» стало бы в тестах недостижимым.

## Защита форм

| Слой | Что делает | Что видит бот |
| :---- | :---- | :---- |
| CSRF | Роут в группе `web`, `@csrf` в форме | 419 без токена |
| `throttle:leads` | Лимит заявок в минуту с одного IP | Ошибка под полем «Телефон» |
| Honeypot `website` | Поле уведено за пределы экрана | **Тот же успех «Заявка принята»**, лид не создаётся |
| Проверка источника | `source_id` сверяется с базой | Ошибка валидации |

Honeypot отвечает боту успехом намеренно — и в обоих форматах ответа. Ошибка валидации назвала бы ему имя поля-ловушки, и после первого прогона ловушка перестала бы работать.

Лимит отвечает ошибкой на форме, а не голым 429, тоже намеренно: за одним IP сидит офис или мобильный оператор, и живой человек должен увидеть «попробуйте через минуту» на форме. Значение — `LEADS_RATE_LIMIT_PER_MINUTE` (по умолчанию 5).

Источник проверяется по-разному: для автомобиля — только существование (проданная карточка живёт ради истории и SEO, заявка с неё легитимна), для услуги — существование **и** публикация (неопубликованной услуги нет ни на одной странице сайта).

## Настройка Telegram-бота

Без токена заявки продолжают сохраняться, а уведомления пропускаются с записью WARN. На локальной машине и в CI так и задумано; на проде это означает, что менеджер не узнаёт о заявках.

`TELEGRAM_MANAGER_CHAT_ID` из окружения — **фолбэк**: с вехи 4.7 адрес получателя персональный у каждого сотрудника и задаётся в его профиле, а общий чат используется, только пока персональных адресов нет ни у кого. Подробности — в [«Уведомлениях сотрудникам»](notifications.md).

**1. Завести бота.** Написать [@BotFather](https://t.me/BotFather), команда `/newbot`, получить токен вида `123456789:AAE...`.

**2. Узнать chat_id менеджера.** Менеджер пишет боту любое сообщение, после чего:

```bash
curl "https://api.telegram.org/bot<ТОКЕН>/getUpdates"
```

В ответе — `"chat":{"id":123456789,...}`. Для группы id отрицательный; бота нужно добавить в группу и снять с него режим приватности, иначе он не увидит сообщений.

**3. Записать в `.env`:**

```dotenv
TELEGRAM_BOT_TOKEN=123456789:AAE...
TELEGRAM_MANAGER_CHAT_ID=123456789
TELEGRAM_TIMEOUT=10
```

**4. Проверить, что токен рабочий:**

```bash
php artisan tinker --execute="dump(Http::get('https://api.telegram.org/bot'.config('services.telegram.token').'/getMe')->json());"
```

Ожидается `"ok" => true`. Если `false` — токен неверный или отозван.

**5. Проверить весь путь целиком** — отправить форму с сайта и убедиться, что сообщение пришло. Это входит в чек-лист запуска (веха 7.2).

Токен не попадает в логи ни на каком уровне, включая текст исключения: в него кладутся только статус и тело ответа, а URL с токеном — нет.

## Очередь и воркер

Уведомления уходят через очередь Redis. Без запущенного воркера задачи копятся и никуда не идут.

```bash
# Локально: composer dev поднимает воркер рядом с сервером
composer dev

# Отдельно
php artisan queue:work --tries=5

# Разово, для проверки
php artisan queue:work --once
```

На проде воркер обязан жить под супервизором (веха 7.1) и перезапускаться после деплоя:

```bash
php artisan queue:restart
```

**Мёртвый воркер снаружи выглядит как работающий сайт.** Заявки пишутся в базу, форма отвечает успехом, менеджер не получает ничего и узнаёт об этом от клиента. Это худший сценарий раздела, и кодом он не закрывается — только присмотром за процессом. Признак: в панели заявки появляются, в Telegram тишина, в `storage/logs/leads.log` есть «заявка принята» и «уведомление поставлено в очередь», но нет «уведомление доставлено».

Повторы: 5 попыток с паузами 10 с, 1 мин, 5 мин, 15 мин и ещё 15 мин. Между попытками менеджер уведомления не получает — при коротком сбое сети сообщение придёт с задержкой, а не потеряется.

## Диагностика

Весь путь заявки пишется в отдельный файл `storage/logs/leads.log` (ротация 30 дней), чтобы его не забивали посторонние записи.

| Запись | Уровень | Значит |
| :---- | :---- | :---- |
| `заявка принята` | INFO | Лид записан в базу. С вехи 4.17 в контексте есть `consent_policy_version` — редакция политики, на которую согласился клиент |
| `уведомления поставлены в очередь` | INFO | Задачи ушли в Redis. В контексте — число получателей по каналам и признак `fallback` |
| `получателей уведомлений нет ни по одному каналу` | WARN | Заявка сохранена, но о ней никто не узнает |
| `уведомление доставлено в Telegram` | INFO | Сообщение ушло на адрес, чей хвост в `chat_id_tail` |
| `Telegram не сконфигурирован` | WARN | Пустой токен — уведомление пропущено |
| `уведомление менеджеру не доставлено` | ERROR | Пять попыток исчерпаны |
| `заявка отброшена по honeypot` | DEBUG | Бот |
| `сработал лимит заявок` | DEBUG | Отказ по IP. В контексте `expects_json` — какой формат ответа получил клиент |

Записи браузерных уведомлений и подписок — в [отдельной таблице](notifications.md#диагностика), файл лога тот же.

Персональные данные клиента в лог не пишутся: только id заявки, источник и адрес страницы. В записи о финальном провале — последние четыре знака телефона, чтобы менеджер опознал заявку, о которой не узнал.

```bash
# Что происходило с заявками сегодня
tail -f storage/logs/leads-$(date +%F).log

# Задачи, упавшие окончательно
php artisan queue:failed

# Повторить упавшие
php artisan queue:retry all
```

Типичные ситуации:

| Симптом | Причина | Что делать |
| :---- | :---- | :---- |
| Заявки в панели есть, в Telegram нет | Воркер не запущен | Поднять `queue:work`, проверить супервизор |
| В логе WARN «не сконфигурирован» | Пустой токен | Заполнить `.env`, `php artisan config:clear` |
| В логе WARN «получателей нет» | Никто не включил уведомления, общий чат пуст | См. [«Уведомления сотрудникам»](notifications.md) |
| Форма «зависла», в консоли ошибка разбора JSON | Ответ пришёл не в JSON — обычно из-за редиректа | Проверить, что ошибки отдаются кодом, а не редиректом |
| В логе ERROR, задачи в `queue:failed` | Токен отозван или бот заблокирован | Проверить `getMe`, затем `queue:retry all` |
| Клиент жалуется «форма не отправляется» | Лимит по IP (офис за одним адресом) | Проверить DEBUG «сработал лимит», поднять `LEADS_RATE_LIMIT_PER_MINUTE` |
| Форма молчит, заявки нет | Honeypot заполнен автозаполнением | Проверить DEBUG «отброшена по honeypot» |
| Формы на сайте нет ни на одной странице | Приём заявок выключен (умолчание после выката) | Тумблер «Приём заявок» на вкладке «Персональные данные» — включать **после** подачи уведомления в Роскомнадзор |
| `POST /leads` отвечает 403 | Тот же выключатель | В логе WARN «приём заявок выключен» с IP и `referer` |
| Страница `/privacy` пуста | Настройка не заведена на проде | `php artisan laocars:install-legal-settings`, см. [«Прод»](deploy.md#php-artisan-laocarsinstall-legal-settings) |
| В карточке заявки «согласие не зафиксировано» | Заявка до вехи 4.17 либо не из формы сайта | Для новых заявок это дефект — смотреть, доходит ли `consent` до сервера |

## Работа менеджера с заявкой

Раздел **«Заявки»** в панели доступен обеим ролям. Рядом с пунктом меню — счётчик новых заявок.

Список открывается на вкладке **«Новые»**; есть вкладки «В работе» и «Все», фильтры по статусу, типу источника и дате, поиск по имени и телефону. Телефон копируется одним щелчком.

**Заявку нельзя ни создать, ни отредактировать.** Создаёт их сайт; содержимое заявки — слова клиента, и правка телефона «по памяти менеджера» уничтожает единственный след того, что клиент на самом деле ввёл.

Работа с заявкой — статус и комментарии:

| Статус | Откуда | Куда можно перейти |
| :---- | :---- | :---- |
| Новая | Ставится автоматически | «В работу», «Закрыть» |
| В работе | Действие «В работу» | «Закрыть» |
| Закрыта | Действие «Закрыть» | «Вернуть в работу» |

Действия доступны и в строке списка, и в шапке карточки заявки. Подтверждения нет: это триаж на десятки заявок в день. Каждая смена статуса пишется в `leads.log` вместе с автором — по логу видно, кто и когда закрыл заявку.

**Комментарии** живут на карточке заявки. Автор проставляется автоматически и не редактируется. Чужой комментарий править нельзя, удалить — только свой (администратор может любой): лента работы с заявкой это журнал, а не документ.

Удаление заявки уносит её комментарии. Сотрудника, у которого есть комментарии, база удалить не даст — сначала нужно разобраться с его записями.
