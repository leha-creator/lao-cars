# Роли и доступ в админке

Кто из сотрудников что видит в панели, как завести нового и что сделать при первом развёртывании на сервере.

## Две роли

| | Администратор | Менеджер |
| :---- | :----: | :----: |
| Каталог: автомобили, марки, характеристики | ✅ | ✅ |
| Заявки: список, статусы, комментарии | ✅ | ✅ |
| Контент: услуги, команда, отзывы | ✅ | — |
| Медиабиблиотека | ✅ | — |
| Настройки сайта | ✅ | — |
| Пользователи и раздача ролей | ✅ | — |
| Свой профиль и свой пароль | ✅ | ✅ |

Менеджер — это тот, кто ведёт продажи: карточки автомобилей и обработка заявок. Всё, что видит посетитель помимо каталога — тексты, прайс, отзывы, контакты, — правит администратор.

Что именно менеджер делает с заявкой — статусы, комментарии, чего у заявки намеренно нет — описано в [«Заявки и уведомления»](leads.md).

Раздел, закрытый для роли, **не появляется в меню** и отдаёт 403 при прямом переходе по адресу. Пункт меню, ведущий в отказ, — это дефект интерфейса, а не защита, поэтому меню и права строятся из одного источника.

Частичных прав внутри раздела нет: менеджер либо видит раздел целиком, либо не видит вовсе. Первое требование вида «правит автомобили, но не удаляет» — сигнал переходить на полноценный пакет разрешений.

## Как завести сотрудника

**Настройки → Пользователи → Создать.**

- **Роль** по умолчанию — менеджер. Поднимать до администратора нужно осознанно.
- **Пароль** обязателен при создании. Пользователь может сменить его сам на странице профиля — сообщите ему об этом, иначе первоначальный пароль так и останется известен вам обоим.
- При **редактировании** поле пароля можно оставить пустым — тогда пароль не изменится. Заполненное поле пароль заменяет.

### Две вещи, которые панель не даст сделать

**Свою роль изменить нельзя** — поле заблокировано на собственной карточке. Иначе единственный администратор мог бы одним сохранением закрыть себе доступ к настройкам и к списку пользователей.

**Последнего администратора нельзя ни понизить, ни удалить.** Панель покажет уведомление и отменит действие. Сначала назначьте администратором кого-то ещё.

Обе защиты существуют потому, что чинится такая ошибка не из интерфейса: панель продолжит работать, вход будет проходить, но настройки и пользователи окажутся закрыты для всех — до запуска консольной команды или правки базы вручную.

## Свой профиль

Ссылка — в меню пользователя в правом верхнем углу. Там меняются имя, e-mail и пароль; для смены пароля панель спросит текущий.

Профиль доступен обеим ролям: править там можно только себя.

## Первый запуск на сервере

**Обязательный шаг деплоя.** На production сиды пользователей не создают, а роль по умолчанию у новой записи — менеджер. Поэтому первого администратора заводит отдельная команда:

```bash
php artisan laocars:make-admin
```

Команда спросит e-mail, имя и пароль (пароль вводится скрыто). Для неинтерактивного деплоя всё передаётся опциями:

```bash
php artisan laocars:make-admin \
  --name="Иван Петров" \
  --email=admin@laocars.ru \
  --password='...'
```

Команда идемпотентна: если пользователь с таким e-mail уже есть, она повысит его до администратора, а если он уже администратор — ничего не изменит и скажет об этом. Повторный запуск в скрипте деплоя безопасен.

> ⚠️ **`php artisan make:filament-user` для первого запуска не годится.** Это штатная команда Filament, и она спрашивает ровно три поля: имя, e-mail и пароль. Роли среди них нет, поэтому созданный ею пользователь получает значение по умолчанию — менеджер. Повысить его можно только из раздела «Пользователи», куда менеджеру хода нет. Результат: панель работает, войти можно, настройки и пользователи закрыты, и починить это из интерфейса невозможно.

## Демо-данные для разработки

`php artisan db:seed` заводит двух пользователей — **только вне production**:

| E-mail | Роль | Пароль |
| :---- | :---- | :---- |
| `test@example.com` | администратор | `password` |
| `manager@example.com` | менеджер | `password` |

Менеджер заведён специально: ограниченную панель полезно увидеть глазами, а не только в тестах.

## Диагностика

**Менеджер видит раздел, которого видеть не должен.** Проверьте, что у модели есть политика в `app/Policies/` и что она наследует `AdminOnlyPolicy`. Панель работает в строгом режиме авторизации: модель без политики не «разрешена по умолчанию» — обращение к ней падает с `LogicException`.

**После добавления нового раздела панель падает с `LogicException` про strict authorization mode.** Это ожидаемое поведение, а не поломка: у новой модели нет политики. Создайте `app/Policies/<Модель>Policy.php` одной строкой — `final class XPolicy extends AdminOnlyPolicy {}` или `extends StaffPolicy`.

**Панель осталась без администратора.** Запустите `php artisan laocars:make-admin` с e-mail существующего пользователя — он будет повышен.
