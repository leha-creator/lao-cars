# Каталог: фильтры и контракт URL

Как устроен публичный каталог автомобилей: какие GET-параметры он понимает, как работает сортировка, что попадает в индекс поисковика, как ведут себя панель фильтров и фотогалерея без JavaScript и как завести характеристику, по которой можно фильтровать.

Страница живёт по адресу `/catalog`, карточка автомобиля — `/catalog/{slug}`. Обе свёрстаны вехой 4.3 по макету; каркас, шапка, подвал и карточка автомобиля в списке пришли вехой 4.1 — см. [«Дизайн-система и каркас вёрстки»](design-system.md).

## Контракт GET-параметров

Все параметры необязательны, порядок значения не имеет.

| Параметр | Значения | Пример |
| :---- | :---- | :---- |
| `brand` | slug марки из справочника | `?brand=zeekr` |
| `engine` | `petrol`, `diesel`, `hybrid`, `electric` | `?engine=electric` |
| `year_from`, `year_to` | целое от 1950 до «текущий год + 1» | `?year_from=2023&year_to=2025` |
| `price_from`, `price_to` | целое, рубли | `?price_from=3000000` |
| `status` | `in_stock`, `on_order` или `in_transit` | `?status=in_transit` |
| `attr[<ключ>]` | значение динамической характеристики | `?attr[body_type]=Кроссовер` |
| `sort` | `new`, `price_asc`, `price_desc` | `?sort=price_asc` |
| `page` | номер страницы | `?page=2` |

Полный пример: `/catalog?brand=zeekr&engine=electric&year_from=2023&price_to=5000000&attr[body_type]=Кроссовер&sort=price_asc&page=2`.

Марка передаётся slug-ом, а не идентификатором: id в адресной строке — мусор, который к тому же не переносится между окружениями.

**Динамические характеристики живут в пространстве имён `attr[]`, а не в плоских параметрах.** Ключ характеристики заводит администратор, и форма разрешает любой `snake_case` — включая `price`, `status`, `brand` и `sort`. Плоский `?body_type=Седан` читался бы приятнее ровно до того дня, когда кто-то заведёт характеристику с ключом `year`: фиксированный фильтр каталога тихо перестал бы работать. `attr[]` делает коллизию невозможной по построению.

### Что происходит с неправильными параметрами

- **Битый параметр уводит на чистый `/catalog`** — редиректом, а не ошибкой. Если из десяти параметров невалиден один, теряются все десять: для ссылки, которую в большинстве случаев прислал бот или сохранил браузер год назад, это правильный размен. Правила валидации намеренно широкие — типы и границы, а не бизнес-условия, — так что попасть под редирект осмысленным вводом трудно.
- **`?status=sold` не открывает проданные автомобили**, а отбрасывается валидацией: допустимых значений три, а не четыре. Проданные не выпадают из фильтра — они выпадают из выдачи; карточка при этом остаётся доступной по прямой ссылке ради истории и SEO. Список разрешённых значений перечислен вручную и намеренно: собрать его из `CarStatus::cases()` «чтобы не забыть новый статус» — ровно та правка, которая снимет это ограничение, и снимет молча.
- **Перевёрнутый диапазон нормализуется перестановкой.** `?year_from=2025&year_to=2020` показывает автомобили 2020–2025, а не пустой каталог: это обычная ошибка пользователя в двух селектах.
- **`page` не валидируется.** Пагинатор сам приводит значение к числу; страница за пределами последней отдаёт **404**, когда записи есть. Пустая страница с кодом 200 — тонкий контент, который поисковик увидит и запомнит. На пустом каталоге правило не срабатывает: там пусто по существу, а не из-за номера страницы.
- **Значение вне списка допустимых даёт честный ноль,** а не молча снятый фильтр: «нашлось 11» там, где пользователь ждал сужения, хуже пустой выдачи.
- **Неизвестный ключ характеристики просто отбрасывается** — как и ключ характеристики, у которой не стоит флаг «в фильтре».

### Сортировка

| `sort` | Порядок |
| :---- | :---- |
| `new` (умолчание) | Сначала новые |
| `price_asc` | Сначала дешёвые |
| `price_desc` | Сначала дорогие |

«Цена по запросу» уезжает в конец **в обоих направлениях**: в PostgreSQL умолчание `NULLS` зависит от направления, и «сначала дорогие» без явного указания открывалось бы автомобилями без цены.

У каждой сортировки есть tie-breaker по идентификатору. Без него автомобили с совпадающим временем создания — а импорт партии карточек одним прогоном даёт ровно это — расползаются по страницам непредсказуемо: одна карточка попадает и на первую страницу, и на вторую, а другая не попадает никуда.

## Индексация фильтров

Комбинаций фильтров сотни, и каждая даёт свой URL. Правило простое:

- **Канонический адрес списка** — `/catalog` плюс только `page`. Параметры фильтра из него выбрасываются, номер страницы — остаётся: у страницы 2 собственный канонический адрес, иначе её карточки не попадут в индекс никогда.
- **Любой применённый фильтр или неумолчательная сортировка** даёт странице `robots: noindex,follow`. `follow` обязателен — ссылки на карточки со страницы должны обходиться.
- **Пагинация под правило не подпадает.** Чистая вторая страница индексируется.
- `?sort=new` — тот же каталог, что и `/catalog`: уводить его в `noindex` не за что.

## Фильтруемые характеристики

Фильтровать можно по характеристикам двух типов: **«Выбор из списка»** и **«Да / Нет»**. Как завести такую характеристику — в [«Админка каталога»](admin-catalog.md); коротко:

1. Завести характеристику в разделе **Каталог → Характеристики авто**.
2. Выбрать тип «Выбор из списка» и заполнить список допустимых значений (для «Да / Нет» список не нужен).
3. Включить переключатель **«Показывать в фильтре каталога»** — у нефильтруемых типов он не показывается вовсе.
4. Проставить значения автомобилям в их карточках.

Ключ характеристики становится именем GET-параметра: `body_type` → `?attr[body_type]=Кроссовер`. **После создания ключ не меняется** — на нём держатся сохранённые пользователями и роботами ссылки.

**Флаг «в фильтре» гасится автоматически**, если тип характеристики меняют на текст или число. Это делает модель, а не форма: тип правится и из админки, и из сида, и из tinker, а три копии правила неизбежно разъедутся.

### Почему по тексту и числам фильтровать нельзя

Равенство по свободному тексту в фильтре бессмысленно: администратор пишет «Long Range AWD», пользователь такого не наберёт. Числу нужен диапазон, то есть приведение текстовой колонки к числу на каждой строке — запрос, который не покроет ни один индекс.

Диапазоны по числовым характеристикам («клиренс от 180 мм») отложены с названным триггером: первый запрос заказчика на такой фильтр — сигнал заводить отдельные типизированные колонки значений, а не подпирать текстовую.

### Что показывается в форме фильтра

Только варианты, по которым что-то найдётся: марка без доступных автомобилей в списке не появится, отсутствующий тип двигателя — тоже, а значения характеристики пересекаются с реально встречающимися. Вариант, дающий ноль автомобилей, — не «пустая выдача», а сломанное доверие к фильтру.

Счётчиков рядом с вариантами («Кроссоверов: 12») нет намеренно: честный счётчик обязан пересчитываться на каждую комбинацию — это фасетный поиск, а не фильтр каталога, — а нечестный обещает больше, чем показывает после клика.

## Панель фильтров в вёрстке

Панель — обычная `<form method="GET">`. Alpine добавляет поверх ровно одно: отправку формы при изменении любого контрола (`x-on:change` на самой форме — событие `change` всплывает, поэтому один обработчик покрывает и селекты, и радио-пилюли, и числовые поля).

Три вещи, которые выглядят как недоделка и являются решениями:

- **Кнопка «Показать» остаётся на месте при живом авто-сабмите.** Без JavaScript она единственный путь применить фильтр, а кнопка, исчезающая через полсекунды после загрузки, хуже кнопки лишней.
- **Все контролы видны всегда — аккордеона «Ещё фильтры» нет.** Спрятанный блок либо не виден роботу и посетителю без JS (если скрыт в разметке), либо моргает на каждой загрузке страницы (если его схлопывает скрипт). На засеянной базе контролов тринадцать, и панель верстается под перенос строки: `flex-wrap` на десктопе, сетка в две колонки на мобильном.
- **Скрытого поля `page` в форме нет.** GET-форма отправляет только свои поля, поэтому применение фильтра само возвращает на первую страницу. Правка «чтобы не терять страницу» ломает не фильтрацию, а пользователя: за последней страницей контроллер отдаёт 404, и фильтрация со страницы 3 привела бы на ошибку вместо новой выдачи. На отсутствие `name="page"` внутри формы стоит отдельный тест.

Статус («Все / В наличии / Под заказ / В пути») выглядит в макете ссылками, но сделан радиокнопками внутри той же формы: ссылка обязана нести в `href` все остальные параметры, то есть склейку текущего query прямо в шаблоне, а радиокнопка несёт их бесплатно и правильно сбрасывает `page`. Оформление — `sr-only` input плюс `peer-checked:` на подписи.

Селект сортировки стоит в строке результатов, но принадлежит той же форме: отдельная форма потребовала бы скрытых копий всех остальных полей. Из-за этого светлую тему вехи 4.11 строка результатов получает **отдельным** классом, а не вместе с секцией выдачи: пропущенная, она давала тёмную полосу поперёк светлой страницы.

**Каталог светлый целиком** (веха 4.11) — единственная внутренняя страница, по которой заказчик высказался прямо. Для панели фильтров это не только фон: браузер красит нативные селекты сам, и за них отвечает `color-scheme: light` внутри `.theme-light`. Без этой строки все десять выпадающих списков остались бы тёмными на светлой панели — снаружи читается как сломанная форма, а на тёмной ОС разработчика не видно вовсе. Механизм — в [дизайн-системе](design-system.md#две-темы-тёмная-по-умолчанию-и-светлые-секции).

**Триггер пересмотра назван:** если администратор пометит «в фильтре» столько характеристик, что панель перевалит за три ряда, фильтр переезжает в боковую колонку — а не прячется под кнопку.

### Пагинация

Список использует собственный вид `resources/views/pagination/catalog.blade.php`, который передаётся **именем** в `$cars->links('pagination.catalog')`. Ставить его через `Paginator::defaultView()` нельзя: этот статик подменяет вид у любого Livewire-компонента с `WithPagination` и возвращает прежний только при штатном уничтожении компонента — которого при HTTP-запросе к странице Filament не происходит. Публикация вида под вендорным именем в `resources/views/vendor/pagination/` — та же глобальная подмена под другим соусом.

Ссылки пагинации несут `rel="prev"` / `rel="next"` и подписаны словом («Страница 2»), активная помечена `aria-current="page"`. Мёртвых стрелок нет: на первой странице не рендерится «назад», на последней — «вперёд».

## Карточка автомобиля

### Фотогалерея

Галерея работает без JavaScript, и это определяет её разметку:

- **все снимки лежат в разметке стопкой**, показывается один — робот и посетитель без скрипта видят все фотографии, а не одну;
- **миниатюры — настоящие ссылки** (`<a href>`) на полноразмерные файлы, а не кнопки: без скрипта это единственный способ посмотреть остальные снимки. Alpine перехватывает клик и подменяет главное фото;
- **стрелки и счётчик существуют только для JS** и скрыты `x-cloak`: контрол, который ничего не делает, обманывает. При единственной фотографии они не рендерятся вовсе.

Главное фото — LCP страницы: `fetchpriority="high"` и никакого `loading`. Миниатюры грузятся лениво.

`srcset` у главного фото нет осознанно: дескриптор `w` обязан быть настоящей шириной файла, а `ImageProcessor` ширину только ограничивает сверху и не апскейлит — снимок 800px остаётся 800px, и дескриптор `1920w` на нём заставил бы браузер выбрать заведомо не тот файл. **Веха 4.14 завела колонки `width`/`height`, но правило этим не снимается:** хранить ширину и апскейлить — разные вещи, сервис по-прежнему не увеличивает, и врать в дескрипторе по-прежнему нечем. Триггер возврата остался прежним — «properly size images» в Lighthouse и средний вариант в `ImageProcessor`.

### Кадр вписывается, а не обрезается (веха 4.14)

Заказчик: «в карточках автомобилей обрезаются фотографии, нужно добавить поддержку любого размера изображения». Выбран вариант из трёх: **контейнер `aspect-ratio` остаётся, `object-cover` меняется на `object-contain`.** Фотография вписывается целиком, поля закрывает `bg-photo`.

Отклонён вариант «карточка по пропорциям файла»: одна вертикальная фотография в ряду из трёх делает ряд вдвое выше и разносит сетку каталога, а смесь 4:3, 16:9 и 3:4 в одном списке — гарантированный «сайт поехал» на приёмке.

**Миниатюры остались `object-cover`,** и разъезд с главным кадром сознательный: миниатюра — указатель на кадр, а не сам кадр, и вписанная целиком в пятую часть ширины она превращается в марку с полями во всю плитку. Сторож на это стоит в `CatalogShowTest` — иначе следующий читатель «поправит».

Тёмная тема получила новое значение `--color-photo`. До вехи поля были видны только на время загрузки, и светло-серая заглушка не мешала; теперь они постоянные, и светло-серый прямоугольник вокруг каждого снимка на тёмной карточке — ровно то, чего тёмная тема избегает. Значение чуть светлее `--color-surface`: поле отличимо от карточки и не спорит с самим кадром.

### Размеры файла в базе

`car_photos` и `media` хранят `width`, `height` и `watermarked_at` (веха 4.14). Все три nullable: у файлов, залитых раньше, этих данных нет, пока по ним не пройдёт `php artisan images:restamp`.

Размеры заведены не ради `srcset`, а ради лайтбокса: «открыть в полном размере» обязано знать, есть ли у файла размер, которого не видно в карточке, — иначе кнопка зума предлагается и для снимка 800px, который крупнее не станет. Побочно закрылась давняя дыра — `width`/`height` у тега `img`.

Атрибуты проставлены **только главному кадру страницы автомобиля**: там `src` и есть тот файл, чьи размеры записаны. На карточке каталога `src` — превью другой ширины, и те же числа были бы враньём того же сорта, из-за которого в проекте запрещён `srcset` без настоящих ширин. Место там и так держит контейнер.

### Просмотр в полный размер

`resources/js/photo-lightbox.js`, регистрируется в `app.js` через `Alpine.data()` до `Alpine.start()` — прецедент `leadForm`, обоснование в разделе «Alpine на публичных страницах» дизайн-системы.

Умеет: зум колесом, двойным кликом и щипком, перетаскивание приближённого кадра, стрелки и клавиши, `Escape`, ловушку фокуса, возврат фокуса на открывший элемент, блокировку прокрутки страницы. Разметка — один блок на страницу, а не копия на каждый кадр.

Кнопка зума не предлагается, когда `width` файла не больше ширины окна: предложение приблизить без эффекта читается как поломка.

**Без JS лайтбокс не нужен и не мешает:** главный кадр обёрнут в `<a href>` на оригинал, как и миниатюры, и клик открывает файл штатным просмотрщиком браузера.

**Автомобиль без фотографий отдаёт страницу с подписью «Фотографии готовятся»,** а не пустым прямоугольником: пустой прямоугольник читается как недогруженная страница. В лог при этом уходит `WARN [Каталог]`.

### Сетка характеристик

Одна сетка на фиксированные и динамические характеристики: сначала марка/модель, год, двигатель, привод и пробег, затем группы справочника («Кузов и салон», «Комплектация», «Импорт») — каждая со своим подзаголовком во всю ширину. Характеристики без группы идут последними, без заголовка.

Разносить фиксированные и динамические по разным блокам отклонено: для посетителя «Кузов» и «Привод» — одна и та же таблица, а разделение выдало бы внутреннее устройство базы.

### Meta-теги

`<title>` и `<meta name="description">` карточки берутся из полей **«SEO-заголовок»** и **«SEO-описание»** в карточке автомобиля (админка → Каталог → Автомобили). Пустое поле даёт фолбэк, собранный из марки, модели и года:

| Поле админки | Колонка | Что будет, если пусто |
| :---- | :---- | :---- |
| SEO-заголовок | `meta_title` | `<марка> <модель>, <год> — ЛАО КАРС` |
| SEO-описание | `meta_description` | `Купить <марка> <модель> <год> года в ЛАО КАРС.` |

Фолбэк живёт в шаблоне карточки, а не в layout: общий фолбэк в layout маскировал бы забытую секцию у остальных страниц.

Канонический адрес карточки — `url()->current()` без query-строки. Отдельной секции у карточки нет: умолчание layout уже даёт нужный адрес, и заход с `?utm_source=…` не плодит дублей.

### Микроразметка

Карточка отдаёт один тег `<script type="application/ld+json">` с двумя объектами: `Car` и `BreadcrumbList`. Собирает их `App\Services\CarStructuredData`.

JSON-LD, а не `itemprop` по вёрстке: микроформаты атрибутами привязывают SEO к раскладке — любая переверстка ломает разметку молча, и заметить это можно только в Search Console через недели.

Состав объекта `Car`: `name`, `url`, `brand`, `model`, `vehicleModelDate`, `image` (все фотографии), `description`, `itemCondition`, `fuelType`, `vehicleEngine`, `driveWheelConfiguration`, `mileageFromOdometer`, `bodyType` и `offers`. Тип один — `Car`: в schema.org он входит в `Vehicle`, а тот в `Product`, поэтому «двойной» тип не нужен.

| Данные карточки | Что уходит в разметку |
| :---- | :---- |
| Пробег не заполнен | `itemCondition: NewCondition`, ключа `mileageFromOdometer` нет |
| Пробег заполнен | `itemCondition: UsedCondition`, `mileageFromOdometer` с `unitCode: KMT` |
| Цена не заполнена | **`offers` отсутствует целиком** |
| Статус «В наличии» | `availability: InStock` |
| Статус «Под заказ» | `availability: PreOrder` |
| Статус «В пути» | `availability: BackOrder` |
| Статус «Продан» | `availability: SoldOut` |
| Характеристика с ключом `body_type` | `bodyType` со значением; без неё ключа нет вовсе |
| Нет ни одной фотографии | ключа `image` нет, в лог уходит `WARN` |

**«В пути» — это `BackOrder`, а не `PreOrder`.** Разница в словаре содержательная: `PreOrder` означает товар, который ещё не выпущен и получить его нельзя в принципе, а `BackOrder` — заказан и придёт позже. Автомобиль в пути уже куплен и физически едет, то есть это второе. `PreOrder` остаётся у «Под заказ», где он и верен.

**Автомобиль без цены не получает `offers` вовсе.** `Offer` без `price` невалиден, а выдуманный ноль означает «отдаём даром» — и именно так его прочитает агрегатор. «Цена по запросу» — это отсутствие предложения в терминах schema.org.

Разметка печатается через `@json` с флагом `JSON_HEX_TAG`. Это единственное место, где данные из базы попадают в HTML без экранирования Blade: закрывающий тег скрипта, вписанный администратором в описание, без этого флага закрыл бы тег по-настоящему и превратил остаток страницы в разметку. На флаг стоит отдельный тест — без него его уберут при первом же рефакторинге как «лишний».

### Какие поля админки на что влияют

| Где | Поле | На что влияет на публичной странице |
| :---- | :---- | :---- |
| Автомобиль | SEO-заголовок, SEO-описание | `<title>` и `<meta name="description">` карточки |
| Автомобиль | Описание, История | Блоки под сеткой характеристик; описание уходит и в `description` разметки |
| Автомобиль → Фотографии | Порядок перетаскиванием | Первая фотография становится главной — и в галерее, и в списке каталога |
| Характеристика | «Показывать в карточке» | Попадает ли строка в сетку характеристик |
| Характеристика | «Показывать в фильтре каталога» | Появляется ли селект в панели фильтров |
| Характеристика | Группа | Подзаголовок в сетке; пустая группа выводится последней без заголовка |
| Характеристика с ключом `body_type` | Значение | `bodyType` в микроразметке |

## Похожие автомобили

Блок на карточке собирается двумя запросами: сначала автомобили той же марки, ближайшие по цене; если их не хватило — добор из других марок в коридоре ±30% от цены. У автомобиля без цены коридора не существует, поэтому для него добор идёт просто по свежим доступным — блок не пустеет.

Размер блока — `catalog.similar_limit`.

## Настройки

| Ключ конфига | Умолчание | Переменная окружения |
| :---- | :---- | :---- |
| `catalog.per_page` | 9 | `CATALOG_PER_PAGE` |
| `catalog.similar_limit` | 3 | `CATALOG_SIMILAR_LIMIT` |

Девять карточек — три ряда трёхколоночной сетки макета. Оба значения читаются через `env()` **внутри конфига**: вызов `env()` из контроллера после `php artisan config:cache` вернёт `null`.

## Индексы под фильтры

Каталог опирается на четыре индекса, заведённых миграцией `add_catalog_filter_indexes`:

| Индекс | Что обслуживает |
| :---- | :---- |
| `cars_available_created_index` | Выдача по умолчанию и пагинация |
| `cars_available_brand_index` | Фильтр по марке вместе с умолчательной сортировкой |
| `cars_available_price_index` | Диапазон цены и сортировка по ней |
| `car_attribute_values_filter_index` | Фильтр по динамической характеристике |

Три первых — частичные, с предикатом `status IN ('in_stock', 'on_order', 'in_transit')`: он записан **тем же списком**, каким его строит выборка доступных автомобилей. Планировщик выводит `status = 'in_stock'` из этого списка, а `status <> 'sold'` — уже нет.

### Правило: предикат индекса обязан совпадать со списком статусов `Car::available()`

Это самое опасное место каталога, и опасно оно тем, как выглядит поломка.

Новый статус автомобиля колонке `cars.status` миграции не требует: это обычная `string`, и четвёртое значение перечисления ложится в неё без правки схемы. Отсюда напрашивается вывод «миграция не нужна» — он был сделан по этому самому коду при разборе требований к статусу «В пути», и он неверен.

Как только `Car::available()` начинает перечислять новый статус, старый предикат под запрос не подходит, и **ни один из трёх индексов больше не берётся**. При этом:

- ошибки нет — запросы остаются корректными;
- красного теста нет — выдача остаётся правильной;
- в логах пусто.

Симптом появляется только на проде с настоящим каталогом и выглядит как «сайт тормозит», а не как «забыли индекс». Расхождение опасно в обе стороны: сужённый скоуп при расширенном индексе даёт ту же потерю.

Поэтому:

- **расширение или сужение списка статусов в `Car::available()` требует новой миграции**, пересоздающей все три частичных индекса (`DROP INDEX IF EXISTS` + `CREATE INDEX`), и её `down()` обязан возвращать прежний предикат;
- на связку стоит сторож в `tests/Feature/Services/CatalogFilterTest.php`: он сверяет фактические предикаты из `pg_indexes` со списком статусов, который скоуп выдаёт в bindings, и падает при расхождении в любую сторону. Комментарий в миграции здесь уже был — и его оказалось недостаточно;
- `CREATE INDEX CONCURRENTLY` не используется: он не работает внутри транзакции, а миграции Laravel на PostgreSQL транзакционные по умолчанию. Триггер пересмотра — каталог вырос настолько, что пересоздание индекса стало заметной паузой при выкладке.

**Индекс по характеристикам построен по выражению `left(value, 64)`, и запрос повторяет это выражение.** Обычный индекс по колонке завести нельзя: запись b-tree ограничена 2704 байтами, а значение характеристики — `text`, куда вставленная копипастом комплектация ляжет целиком и уронит вставку. Поэтому запрос идёт двумя условиями: префикс сужает по индексу, точное равенство подтверждает совпадение.

Отсюда два правила, которые легко нарушить «упрощением»:

- **Условие `left(value, 64) = ?` убирать нельзя.** Выдача останется верной, а индекс молча выключится — регрессия, которую не поймает ни один функциональный тест. Её стережёт отдельная проверка `toSql()`.
- **Длину префикса нельзя поменять правкой константы.** `App\Support\AttributeFilterIndex::PREFIX_LENGTH` берут и миграция, и запрос; правка константы не пересоздаёт индекс, и запрос просто перестанет его брать. Менять длину можно только новой миграцией. Расхождение стережёт проверка по `pg_indexes`.

Кеша у вариантов фильтра нет: несколько лёгких запросов на показ каталога дешевле, чем инвалидация, завязанная сразу на три модели. Триггер пересмотра конкретный — каталог за тысячу карточек либо заметная доля времени ответа на этих запросах.

## Диагностика

**Фильтр по характеристике ничего не находит, хотя значения проставлены.** Проверьте флаг «Показывать в фильтре каталога» у характеристики и совпадение значения со списком допустимых — регистр и опечатки значимы.

**Переключателя «Показывать в фильтре каталога» нет в форме.** Тип характеристики — текст или число, по ним фильтровать нельзя.

**Ссылка с фильтром открывает пустой каталог без фильтров.** Один из параметров не прошёл валидацию — например, марка была переименована или удалена. Это штатное поведение, а не ошибка.

**Вторая страница показывает выдачу без фильтров.** Ссылка построена без сохранения query-строки. Все ссылки пагинации обязаны нести параметры фильтра.

**Фильтр не применяется сам при смене селекта.** Не выполнился JavaScript — проверьте консоль и что фронтенд собран (`npm run build`). Это не поломка: кнопка «Показать» применяет фильтр и без скрипта.

**Пагинация выглядит светлой, кнопками вместо ссылок.** В рантайм пробрался `Paginator::defaultView()` — обычно его ставит Livewire-компонент с `WithPagination` и не возвращает обратно. Список каталога обязан звать `links('pagination.catalog')` явно.

**Галерея не листается, но фотографии видны.** Alpine не инициализировался. Разметка при этом полноценна: миниатюры — ссылки на полноразмерные файлы, ими и можно пользоваться.

**Карточка без фотографий показывает подпись вместо галереи.** Фотографии не загружены в админке; в `storage/logs/laravel.log` при этом лежит `WARN [Каталог]` с id автомобиля. Микроразметка такой карточки уходит без `image`, и на расширенный сниппет она не претендует.
