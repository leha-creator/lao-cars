# Инфопанель администратора: сервер, службы, посещаемость

Страница для разработчика: как устроены блоки главной страницы панели (`/admin`), откуда берётся каждое число и что проверять, когда оно врёт. Инструкция сотруднику — статья «Инфопанель: сервер и посещаемость» в разделе «Справка» панели.

Блоки видит только администратор. Менеджеру на той же странице остаётся карточка учётной записи.

## Два инварианта

**1. Статистика не имеет права уронить или задержать запрос.** Инвариант того же ранга, что «заявка не должна теряться». Учёт идёт в `terminate()` middleware `RecordRequestMetrics` — под php-fpm это после `fastcgi_finish_request()`, посетитель ответ уже получил; тело целиком в `try/catch (Throwable)` с `WARN` в лог.

**2. На пути запроса нет ни одного запроса к PostgreSQL.** Только Redis, в который и так ходит каждый запрос (сессии, кеш настроек). `INSERT` на просмотр выглядит проще, но добавлял бы запрос к базе каждой публичной странице, а на счётчик запросов завязаны сторожа `LayoutTest`, `HomePageTest` и страницы 500 (та обязана обходиться без базы вовсе).

Сторожа обоих — `tests/Feature/Http/RequestMetricsTest.php`: `adds no database query to a public page` и `serves the page when the accounting itself fails`.

## Путь просмотра

```
запрос → ответ отправлен → RecordRequestMetrics::terminate()
            ├─ RequestCounter::hit()      HINCRBY analytics:requests:{YmdH}
            └─ VisitRecorder::record()    RPUSH  analytics:views   (если это просмотр)

раз в минуту:  analytics:flush  →  LRANGE + LTRIM  →  один INSERT в page_views
раз в сутки:   analytics:prune  →  удаление строк старше недели и сверх потолка
```

Отсюда два свойства, о которых спросят: статистика **отстаёт до минуты** и **целиком зависит от планировщика**. Второе закрыто отметкой пульса — см. «Службы» ниже.

Middleware зарегистрирован **глобально** (`bootstrap/app.php`), а не в группе `web`: панель Filament собирает свой стек и в `web` не входит, а счётчик обязан видеть и её. Запросы за время `artisan down` сюда не доходят — их отбивает `PreventRequestsDuringMaintenance` раньше, поэтому окно выката не рисует ложный всплеск 5xx.

## Что считается просмотром страницы

`VisitRecorder::shouldRecord()` — всё одновременно:

- метод `GET`, ответ `200`, `Content-Type: text/html`;
- маршрут не из панели (`filament.*`), путь не из `analytics.ignore_paths` (`up`);
- не робот (`BotDetector`: регулярное выражение `analytics.bot_pattern` плюс пустой User-Agent);
- не предзагрузка (`Sec-Purpose` / `Purpose: prefetch`);
- **не вошедший сотрудник** (`auth()->check()`): менеджер, проверяющий карточку после правки, иначе накручивал бы статистику сам себе.

Правило **исключающее**, а не белый список маршрутов: новая публичная страница начинает считаться сама.

Адрес хранится **без строки запроса** — комбинаций фильтров каталога сотни, и «топ страниц» рассыпался бы на единичные строки. UTM-метки вынимаются отдельными колонками. Для `catalog.show` пишется `car_id` из уже привязанной маршрутом модели.

## Таблица `page_views`

| Колонка | Что в ней |
| :---- | :---- |
| `viewed_at` | Момент просмотра, московское время (`timestamp` без пояса) |
| `path`, `route_name` | Адрес без строки запроса и имя маршрута |
| `car_id` | Автомобиль карточки; `nullOnDelete` |
| `visitor_hash` | Хеш посетителя, 32 hex-символа |
| `is_entry` | Заход извне или прямой — а не переход внутри сайта |
| `referrer_host` | Только хост источника: путь и строка запроса чужой страницы не хранятся |
| `utm_source`, `utm_medium`, `utm_campaign` | Рекламные метки |
| `device` | `desktop` / `mobile` / `tablet` |

**Колонок IP и User-Agent нет и не появляется.** **Хеш посетителя не связывается с заявкой** — ни колонки `visitor_hash` в `leads`, ни «пути клиента до заявки»: со связью обезличенная статистика становится профилированием конкретного человека. Оба запрета записаны в PHPDoc `PageView` и стерегутся `PageViewTest`.

Состав таблицы описан в разделе 13 политики обработки ПДн. Меняете, что хранится, — это новая редакция политики до выката.

## Как считаются посетители

`visitor_hash = sha256(соль | IP | User-Agent)`, обрезанный до 32 символов. Соль — 32 случайных байта **на каждый день**, создаётся первым запросом дня (`SET NX`, срок 48 часов) и живёт только в Redis. Когда ключ истёк, сопоставить хеш с IP нельзя ничем.

Обратная сторона: посетитель уникален **внутри дня**. За период считается `count(distinct (дата, хеш))`, то есть человек, заходивший три дня подряд, посчитан трижды. Поэтому карточка называется «Посетители (по дням)», а не «Уникальные за неделю», и то же сказано в справке. Сторож — `counts a visitor who came back the next day twice` в `TrafficReportTest`.

`trustProxies` в проекте не настроен. За обратным прокси у всех посетителей один IP, и различаются они только по User-Agent — уникальные занижены. Перед приёмкой проверьте, что трафик не идёт через прокси со старого сервера.

## Ключи Redis

Все ключи учёта лежат в соединении `default` через `Redis::connection()`, **а не в кеше**. `deploy.sh` на каждом выкате делает `optimize:clear`, а он чистит хранилище кеша целиком: соль в кеше пропадала бы при каждом релизе, и «уникальные за день» молча удваивались бы.

| Ключ | Тип | Срок | Что это |
| :---- | :---- | :---- | :---- |
| `analytics:requests:{YmdH}` | hash | 8 суток | Счётчик запросов за час |
| `analytics:views` | list | — | Буфер просмотров, потолок `analytics.buffer_limit` |
| `analytics:salt:{Y-m-d}` | string | 48 часов | Суточная соль хеша посетителя |
| `analytics:views:overflow-warned` | string | 15 минут | Замок предупреждения о переполнении буфера |
| `ops:heartbeat:flush` | string | сутки | Когда последний раз отработала `analytics:flush` |
| `ops:heartbeat:prune` | string | трое суток | Когда последний раз отработала `analytics:prune` |
| `ops:warned:*` | string | 15 минут | Замки предупреждений сервисов `ServerStatus` и `OpsStatus` |

К именам добавляется префикс соединения (`database.redis.options.prefix`).

**В тестах** эти ключи сбрасывает `resetAnalytics()` из `tests/Pest.php` — `Cache::flush()` их не трогает. Помощник удаляет только свои ключи: `FLUSHDB` запрещён, в той же базе живёт очередь. Ловушка, из-за которой он написан руками: predis дописывает префикс к ключу в `DEL`, но **не** к шаблону `SCAN`, а найденные ключи возвращает уже с префиксом.

## Счётчик запросов

Поля корзины: `site_2xx`, `site_3xx`, `site_4xx`, `site_5xx`, `panel`, `system`, `bot`. Порядок проверок в `RequestCounter::classify()` значим: панель (`admin`, `livewire*`) и служебные адреса определяются по пути **раньше** робота.

`panel` выделен намеренно: колокольчик опрашивает панель каждые 30 секунд с каждой вкладки, и без разделения три вкладки сотрудников выглядели бы как посещаемость.

Считается то, что дошло до PHP. Статику отдаёт nginx, и её здесь нет; разбор лога nginx отклонён — файл принадлежит `www-data:adm`, а пул работает от `laocars`. Точность — час: «последний час» в 14:35 показывает корзины 13:00 и 14:00 целиком.

## Хранение

- `analytics.retention_days = 7` — `analytics:prune` удаляет строки старше начала дня «сегодня минус 7». Период «7 дней» в фильтре — сегодня и шесть предыдущих дней, поэтому он всегда полный.
- `analytics.max_rows = 500 000` (около 100 МБ) — второй предохранитель: сверх потолка удаляются самые старые строки, пишется `WARN`.
- `analytics.buffer_limit = 20 000` — потолок буфера в Redis. Остановившийся планировщик теряет самые старые просмотры, а не память Redis.

Чистка идёт в 03:10 — до бэкапа базы в 03:30, чтобы дамп не возил удаляемое. `php artisan analytics:prune --dry-run` показывает числа и ничего не удаляет.

## Службы: файл состояния

Бэкапы лежат в каталоге с режимом `0700` от root, сертификат — в `/etc/letsencrypt`, `systemctl` и `docker` пулу php-fpm недоступны намеренно. **PHP ничего не исполняет** — всё приносит `deploy/healthcheck.sh` (cron от root, раз в пять минут) файлом `/var/log/laocars/status.txt`:

```
generated_at=2026-10-07T12:35:01+03:00
problem=воркер laocars-queue не запущен
backup_db_at=2026-10-07T03:30:12+03:00
backup_media_at=2026-10-05T04:30:40+03:00
ssl_not_after=2026-11-12T08:14:00+03:00
```

Строки `ключ=значение`, строка `problem=` повторяется. **Не JSON**: `jq` на сервере нет, а экранирование руками в bash — место для тихой порчи файла первой же кавычкой. Запись атомарная (`mktemp` + `mv`), режим `0644`. **В файле не должно быть ни одного секрета** — добавляя проверку в `healthcheck.sh`, смотрите, что уходит в `problems+=`.

`OpsStatus` разбирает файл терпимо: нераспознанные строки пропускаются, файл без читаемого `generated_at` считается отсутствующим. `generated_at` старше `ops.status_max_age_minutes` (15) — карточка «Мониторинг» краснеет: остановившийся cron иначе выглядел бы как вечное «всё в порядке».

Остальные карточки блока:

| Карточка | Источник | Порог |
| :---- | :---- | :---- |
| Очередь | `Queue::size()` и `failed_jobs` | красная при упавших задачах |
| Статистика | `ops:heartbeat:flush` | красная, если отметки нет или она старше `ops.heartbeat_max_age_minutes` (10) |
| Бэкап базы | `backup_db_at`, в описании `backup_media_at` | жёлтая старше 26 часов |
| Сертификат | `ssl_not_after` | красная меньше 14 дней |
| Версия | `storage/app/deploy.json` от `deploy.sh` | — |

Локально и в CI файлов нет — блок серый, «Нет данных». Это штатно.

## Сервер

`ServerStatus` читает то, что PHP отдаёт сам:

- диск — `disk_total_space()` / `disk_free_space()` от корня проекта;
- память — `/proc/meminfo`, именно **`MemAvailable`**, а не `MemFree`: свободной памяти на здоровом Linux почти нет, она занята кешем;
- нагрузка — `sys_getloadavg()` рядом с числом ядер из `/proc/cpuinfo`.

Порог диска `ops.disk_warning_percent = 85` — **то же число, что `DISK_THRESHOLD` в `healthcheck.sh`**. Одно знание в двух местах; совпадение стережёт `ServerStatusTest`.

Показывается текущее значение. Графиков во времени нет намеренно — это задача Netdata или Zabbix, а не страницы панели.

## Страница и виджеты

`App\Filament\Pages\Dashboard` наследует штатную страницу, добавляет фильтр периода (`HasFiltersForm`, перечисление `AnalyticsPeriod`) и задаёт порядок виджетов в `getWidgets()`. Фильтр один на страницу: запросы и посещения за разные периоды рядом сравнить нельзя.

| Виджет | Тип | Данные | Опрос |
| :---- | :---- | :---- | :---- |
| `OpsStatusWidget` | сводка | `OpsStatus` | 60 с |
| `ServerStatsWidget` | сводка | `ServerStatus` | 60 с |
| `RequestsChartWidget` | столбцы | `RequestCounter` | 60 с |
| `TrafficStatsWidget` | сводка | `TrafficReport::summary()` | нет |
| `VisitsChartWidget` | линии | `TrafficReport::series()` | нет |
| `TopPagesWidget` | таблица | `TrafficReport::topPages()` | нет |
| `TrafficSourcesWidget` | таблица с группами | `sources()` и `campaigns()` | нет |
| `TopCarsWidget` | таблица | `topCars()` и `devices()` | нет |

Два правила, на которые стоят сторожа в `DashboardGuardTest` — оба перебирают **каталог** `app/Filament/Widgets`, а не список в тесте:

- **Каждый виджет использует трейт `AdminOnly`.** Виджет — не ресурс, политика к нему не применяется, и строгий режим авторизации виджеты не закрывает: штатный `canView()` возвращает `true` всем.
- **Каждый виджет объявляет `$pollingInterval` в своём классе.** Умолчание трейта `CanPoll` — `5s`: восемь виджетов на нём дают восемь запросов Livewire каждые пять секунд с каждой вкладки, и инфопанель сама становится нагрузкой, которую показывает.

Новый виджет обязан попасть и в `Dashboard::getWidgets()` — иначе он не виден никому; это тоже ловит сторож.

Виджеты запросов не пишут: всё чтение `page_views` — в `TrafficReport`.

## Конфигурация

`config/analytics.php` и `config/ops.php`. Из окружения читаются:

| Переменная | Умолчание | Зачем |
| :---- | :---- | :---- |
| `ANALYTICS_ENABLED` | `true` | Выключатель учёта целиком |
| `OPS_STATUS_FILE` | `/var/log/laocars/status.txt` | Файл состояния от `healthcheck.sh` |
| `OPS_DEPLOY_FILE` | `storage/app/deploy.json` | Отметка выката |
| `OPS_PROC_PATH` | `/proc` | Нужен тестам и съёмке справки на Windows |

**На проде `ANALYTICS_ENABLED=false`, пока не опубликована редакция политики обработки ПДн с абзацем о статистике посещений** (раздел 13). Действующая редакция говорит, что системы веб-аналитики не установлены и раздел будет дополнен до начала их использования. Порядок: текст в панели → `ANALYTICS_ENABLED=true` в `.env` → `php artisan config:cache`.

## Локальный запуск

Cron на Windows нет, поэтому статистика сама в базу не переезжает:

```bash
php artisan analytics:flush    # перенести буфер руками
php artisan schedule:work      # или держать планировщик запущенным
```

Блоки «Службы» и «Сервер» локально в основном серые: файла состояния нет, `/proc` на Windows тоже. Посмотреть их заполненными — подставить фикстуры из `tests/Fixtures/` переменными `OPS_STATUS_FILE` и `OPS_PROC_PATH`.

## Диагностика

**Посещаемость пустая или застыла.** По цепочке:

1. Карточка «Статистика» в блоке «Службы». Красная — планировщик не запускает `analytics:flush`: `crontab -l` от `laocars` обязан содержать `schedule:run`.
2. `ANALYTICS_ENABLED` в `.env` и `php artisan config:cache` после правки.
3. Буфер: `redis-cli LLEN <префикс>analytics:views`. Растёт — учёт работает, не работает перенос; запустите `php artisan analytics:flush` руками и прочитайте ошибку.
4. Буфер пуст и не растёт — учёт не пишет. В `storage/logs/laravel.log` ищите `[Analytics] учёт запроса не выполнен`.

**В блоке «Сервер» «Нет данных».** Проверять **через саму панель**, а не `php artisan tinker`: у CLI свой `php.ini`, и «в консоли работает» про FPM не говорит ничего. Причина почти всегда в пуле:

```bash
grep -E 'open_basedir|disable_functions' /etc/php/8.5/fpm/pool.d/laocars.conf /etc/php/8.5/fpm/conf.d/*.ini
```

В логе — `[Ops] метрика сервера недоступна` с именем метрики, не чаще раза в 15 минут.

**Блок «Службы» серый на проде.** Файла состояния нет или он не читается от `laocars`: `sudo -u laocars cat /var/log/laocars/status.txt`. Файл пишет cron от **root**; от `laocars` скрипт не прочитает каталог бэкапов.

**«Мониторинг: не обновлялся».** Cron `healthcheck.sh` остановился. В логе приложения — `[Ops] файл состояния не обновлялся`.

**Карточка «Версия» пустая.** `storage/app/deploy.json` появляется после первого выката с новым `deploy.sh`; в `/var/log/laocars/deploy.log` ищите «Отметка выката записана».

**Посетителей подозрительно мало при живом трафике.** Запросы идут через обратный прокси, и у всех один IP — см. «Как считаются посетители».

**Роботы в посещаемости.** Робот представился браузером. Дополните `analytics.bot_pattern`; от неограниченного роста страхует `analytics.max_rows`.

## Что сознательно не делается

| Не делается | Почему |
| :---- | :---- |
| Графики CPU и памяти во времени | Нужен постоянный сборщик метрик — это отдельная система |
| География посетителей | База GeoIP — 60+ МБ с ежемесячным обновлением и лицензией |
| Время на странице, отказы, пути по сайту, воронки | Требуют JS-маячков и идентификатора сессии в cookie; политика ПДн говорит, что cookie одна, техническая |
| Вебвизор, карты кликов, цели | Это Яндекс.Метрика; она остаётся отложенной интеграцией и требует баннера согласия |
| «Сейчас на сайте» | Широковещательный канал ради числа, которое почти всегда 0–2 |
| Просмотр логов в панели | В канале `leads` — телефоны клиентов; логи читаются по SSH |
| Перезапуск служб и запуск бэкапа из панели | Root из веба |
| История дольше недели | Требование постановки. Триггер возврата: заказчик просит сравнить месяц с месяцем — заводится таблица суточных итогов без хешей, сырые просмотры по-прежнему живут неделю |
| Экспорт в CSV | Не просили; на недельном окне выгружать нечего |
