# Прод: устройство, выкат, откат, диагностика

Страница для разработчика: как устроен прод, как на него выкатывать, что делать, когда он лежит. Инструкции сотруднику живут в панели, в разделе «Справка».

## Что где

| Что | Где |
| :---- | :---- |
| Домен | `laocars.ru`, канонический хост — apex; `www` и `http` отдают `301` |
| Сервер | Ubuntu 26.04 LTS, 4 ГБ RAM, 2 vCPU, диск 30 ГБ (корень 28,9 ГБ), `194.67.121.190` |
| Код | `/var/www/laocars`, владелец `laocars`, ветка `master` |
| Конфиг приложения | `/var/www/laocars/.env` — **единственный экземпляр**, в git не попадает |
| Пароль базы | `/var/www/laocars/deploy/.env.docker`, в git не попадает |
| Базы | PostgreSQL 17 и Redis 7 в контейнерах, `compose.production.yml` |
| Веб-сервер | nginx, конфиг симлинком из `deploy/nginx/laocars.conf` |
| PHP | 8.5.4 из штатных репозиториев, отдельный пул `laocars` на `/run/php/laocars.sock` |
| Воркер очереди | systemd-юнит `laocars-queue` |
| Сертификат | Let's Encrypt на оба имени, автопродление certbot'ом |
| Логи | `storage/logs/laravel.log`, `storage/logs/leads-*.log`, `/var/log/laocars/{deploy,queue,backup,healthcheck}.log`, `/var/log/nginx/laocars-*.log` |
| Бэкапы | `/var/backups/laocars/{db,media,config}` |

## Почему приложение не в контейнере

Гибрид: PHP и Node стоят пакетами, в Docker живут только базы.

PHP-слой без контейнера — это отсутствие сборки образа, отсутствие реестра и `git pull` вместо `docker pull` на машине с 2 vCPU. Базы в контейнерах — это фиксированные версии (те же 17 и 7, что локально и в CI), изоляция данных в volume и переносимость на другой сервер одной командой.

Прямое следствие для выката: он идёт `git`-ом и сборкой на месте, а не подменой образа. Отсюда окно maintenance (см. ниже) и отсутствие zero-downtime — понятный следующий шаг, не требующий переделки сделанного.

## Как выкатить

Три пути, и все три делают ровно одно и то же — запускают `deploy/deploy.sh` на сервере.

**Автоматически.** Пуш в `master` → зелёный CI → workflow `Deploy` выкатывает **тот коммит, который прошёл CI**, а не `HEAD` ветки. Разница существенна: между зелёным прогоном и выкатом в `master` мог приехать ещё один пуш, и выкатывать его означало бы обойти собственный гейт.

**Вручную из интерфейса GitHub.** Actions → Deploy → Run workflow, поле `ref` — SHA или тег. Пустое поле означает `origin/master`.

**Вручную по SSH.**

```
ssh laocars@194.67.121.190
/var/www/laocars/deploy/deploy.sh            # origin/master
/var/www/laocars/deploy/deploy.sh <sha>      # конкретная ревизия
```

Выкат занимает **около 15 секунд**, когда зависимости не менялись, и до двух минут, когда `composer install` и `npm ci` реально что-то ставят. Всё это время сайт отдаёт 503 через `artisan down`. Для MVP приемлемо.

### Порядок в `deploy.sh` не произвольный

`php artisan down` и `optimize:clear` идут **до** `git reset --hard`. Причина: `composer install` вызывает `filament:upgrade` через `post-autoload-dump`, то есть поднимает приложение. Между `reset` и `composer install` на диске лежит новый код со **старым** `vendor/`, и любая артизан-команда в этом промежутке падает, как только релиз добавил зависимость.

В обратном порядке первой такой командой оказалась бы сама `down`: она бы не сработала, `trap` с `artisan up` не починил бы ничего, и сайт отдавал бы 500 всем посетителям весь `composer install` и `npm run build`.

### Финальная проверка идёт по HTTPS и это важно

```
curl -fsS --resolve laocars.ru:443:127.0.0.1 https://laocars.ru/up
```

Вариант `curl -H 'Host: laocars.ru' http://127.0.0.1/up` **не годится**: после выпуска сертификата порт 80 отдаёт `301`, а `curl -f` на `3xx` не падает. Без `-L` такая проверка завершается успехом, не дойдя до PHP, — то есть объявляет выкат удачным при мёртвом php-fpm. То же правило действует в `healthcheck.sh`.

## Как откатиться

**Сначала прочитайте это, потом откатывайтесь.**

Откат возвращает **код**. Он **не откатывает миграции**. Если релиз содержал разрушительную миграцию (удалил колонку, переименовал таблицу), порядок обратный: сначала восстановить базу из бэкапа, потом откатывать код. Откат кода поверх изменённой схемы даёт приложение, которое ищет то, чего уже нет.

Сам откат — тот же выкат с другой ревизией:

```
# SHA предыдущей ревизии печатается в начале каждого выката:
grep 'ОТКАТ НА ПРЕЖНЮЮ' /var/log/laocars/deploy.log | tail -1

/var/www/laocars/deploy/deploy.sh <sha>
```

Либо через GitHub: Actions → Deploy → Run workflow → `ref` = SHA.

## Секреты и доступы

`.env` прода собирается на сервере руками и **не копируется с локальной машины**: там `APP_DEBUG=true`, `LOG_LEVEL=debug` и локальные порты.

Ключи, о которых стоит знать отдельно:

- **`APP_KEY`** — потеря делает нечитаемыми сессии и все зашифрованные значения;
- **`VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY`** — генерируются один раз (`php artisan webpush:vapid`) и **не меняются никогда**. Новая пара делает мёртвыми все существующие подписки разом, а сотрудник об этом не узнает: кнопка в кабинете по-прежнему покажет «этот браузер подписан»;
- **`ASSET_URL` остаётся пустым.** Из него собираются адреса всех медиа сайта. Пустое значение даёт относительный `/storage/...`, верный на любом хосте; заполненное переопределяет адрес каждой картинки разом;
- **`SESSION_SECURE_COOKIE=true`** — выставляется только после того, как HTTPS заработал. С `true` по открытому HTTP браузер не отдаёт cookie вовсе, и вход в панель ломается раньше, чем появляется сертификат.

GitHub Actions знает только адрес, пользователя и приватный ключ деплоя: `DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_SSH_KEY`, `DEPLOY_HOST_KEY`. Содержимого `.env` в CI нет и быть не должно.

**Ключ деплоя ограничен принудительной командой.** В `authorized_keys` пользователя `laocars` он прописан с `command="/var/www/laocars/deploy/ci-deploy.sh"` и запретом пробросов. Укравший приватную часть может выкатить ревизию из уже существующего `origin` — и ничего больше: ни оболочки, ни чтения `.env`, ни туннеля внутрь. Проверяется это так:

```
ssh -i <ключ> laocars@194.67.121.190 "cat /var/www/laocars/.env"
# ожидается: ci-deploy: недопустимая ревизия, выкат не выполнен.
```

## Telegram с этого хостинга ходит только по закреплённому адресу

**Это самая неочевидная особенность прода, и она ломает главную функцию сайта, если её не знать.**

`api.telegram.org` резолвится в `149.154.166.110` — и локальным резолвером, и `8.8.8.8`, и `1.1.1.1`. С этого хостинга TCP на этот адрес **не проходит**, уходит в таймаут. При этом GitHub, NodeSource и push-сервисы всех трёх браузеров доступны: блокировка адресная, а не «нет интернета».

Рабочий адрес — `149.154.167.220`, он закреплён в `/etc/hosts`:

```
149.154.167.220 api.telegram.org
```

Без этой строки не уходит **ни одно** уведомление о заявке, при том что сайт снаружи полностью исправен. Роадмап называет этот класс отказа самым дорогим: «сайт работает, сотрудник не узнаёт о заявках».

**Пин хрупкий.** Если Telegram перестанет обслуживать этот адрес, уведомления замолчат снова и снова тихо. Поэтому `healthcheck.sh` отдельно проверяет `getMe` и пишет отказ **в свой лог**, а не только шлёт тревогу тем же каналом, который отказал.

Проверить руками:

```
TOKEN=$(grep '^TELEGRAM_BOT_TOKEN=' /var/www/laocars/.env | cut -d= -f2-)
curl -sS "https://api.telegram.org/bot${TOKEN}/getMe"
```

### «Bad Request: chat not found»

`TELEGRAM_MANAGER_CHAT_ID` — **личный чат**, а не группа. Пока владелец чата не написал боту первым (кнопка Start), Telegram отвечает `403`/`chat not found`, и уведомление пропускается с WARN в канал `leads`. Заявка при этом сохраняется. Лечится одним нажатием Start у `@laocars_bot`.

## Почта отсюда не отправляется

`MAIL_MAILER=log`, SMTP отложен за пределы MVP. Практическое следствие: восстановление пароля через интерфейс невозможно, пароль администратора меняется командой на сервере.

Отдельно: **исходящие SMTP-порты на этом хостинге закрыты** (`smtp.yandex.ru:465` и `smtp.gmail.com:587` уходят в таймаут). То есть поднять почту «просто прописав SMTP» не выйдет — понадобится relay провайдера или сервис рассылки по HTTPS.

## Бэкапы

Cron от `root`: база ежедневно в 03:30, медиа по воскресеньям в 04:30, копия `.env` при каждом запуске.

```
/var/backups/laocars/db/      laocars-YYYYmmdd-HHMM.dump   (pg_dump -Fc, 14 копий)
/var/backups/laocars/media/   media-YYYYmmdd-HHMM.tar.gz   (4 копии)
/var/backups/laocars/config/  env-YYYYmmdd-HHMM            (5 копий, права 600)
```

Восстановление:

```
DUMP=/var/backups/laocars/db/laocars-20260814-0330.dump
C="docker compose -f /var/www/laocars/compose.production.yml exec -T postgres"

$C psql -U laocars -d postgres -c 'CREATE DATABASE laocars_restore_check;' < /dev/null
$C pg_restore -U laocars -d laocars_restore_check --no-owner < "$DUMP"
# сверить количество записей, затем:
$C psql -U laocars -d postgres -c 'DROP DATABASE laocars_restore_check;' < /dev/null
```

`< /dev/null` в этих командах обязателен: `exec -T` подключает stdin к контейнеру, и без перенаправления `psql` съедает остаток вызывающего скрипта. Симптом читается как «команда молча оборвалась на середине».

**Копии лежат на том же диске, и это записанный долг, а не недосмотр.** Они спасают от «удалили не ту запись» и «сломали миграцию», но не от потери сервера. Вынос копии наружу — следующий шаг с названным триггером: первый же реальный контент в каталоге.

**Проверка восстановления делалась на пустой базе** (14.08.2026): совпало число миграций, содержательные таблицы были пусты. То есть проверен механизм, а не объём. **Повторить после наполнения каталога** — иначе первая настоящая проверка совпадёт с первой настоящей аварией.

## Мониторинг

**Локальный** — `deploy/healthcheck.sh`, cron от root каждые 5 минут. Проверяет: ответ `https://laocars.ru/up`, живость воркера, здоровье обоих контейнеров, свободное место (тревога выше 85%), непустой `failed_jobs`, досягаемость Telegram.

Тревога уходит **после двух неудач подряд**, а не после первой: `artisan down` во время выката отдаёт 503 всем, включая `/up`, и однократная неудача в окне деплоя является нормой. Отбой отправляется тоже — иначе непонятно, авария продолжается или прошла. В лог пишутся только смены состояния.

**Внешний** — обязателен и настраивается через веб-интерфейс UptimeRobot или аналога: `https://laocars.ru/up`, раз в 5 минут. Скрипт на упавшем сервере о падении не сообщит.

## Когда сайт лежит

Порядок разбора — от дешёвого к дорогому.

```
# 1. Идёт ли сейчас выкат (503 — это норма на время деплоя)
tail -20 /var/log/laocars/deploy.log

# 2. Отвечает ли приложение изнутри
curl -sSi --resolve laocars.ru:443:127.0.0.1 https://laocars.ru/up | head -3

# 3. Живы ли процессы
systemctl status nginx php8.5-fpm laocars-queue --no-pager | grep -E 'Active|●'
docker compose -f /var/www/laocars/compose.production.yml ps

# 4. Что говорит приложение
tail -50 /var/www/laocars/storage/logs/laravel.log
tail -30 /var/log/nginx/laocars-error.log

# 5. Не забит ли диск (на 28,9 ГБ это реальный сценарий)
df -h /
du -sh /var/backups/laocars /var/www/laocars/node_modules /var/www/laocars/vendor
```

**Сайт застрял в maintenance.** `deploy.sh` снимает его `trap`-ом на выходе, но если процесс убили сигналом — снять руками:

```
cd /var/www/laocars && php artisan up
```

**Уведомления не приходят, а заявки в панели есть.** Смотреть в этом порядке: пин Telegram в `/etc/hosts` (см. выше), `getMe`, `storage/logs/leads-*.log`, `failed_jobs`, живость воркера.

## Что сознательно не сделано

- **Zero-downtime.** Выкат идёт с окном maintenance. Релизы с симлинком — понятный следующий шаг, не требующий переделки сделанного.
- **CSP.** На сайте есть инлайновый JSON-LD и инлайновые `x-data` Alpine: корректная политика требует отдельной работы с nonce, а неверная тихо ломает интерактив.
- **Deploy key для GitHub.** Репозиторий публичный, клон идёт по HTTPS. **Триггер завести ключ названный: репозиторий становится приватным.** В этот момент `git fetch` в `deploy.sh` начнёт падать на аутентификации, и симптом будет читаться как «сломался деплой», а не «сменилась видимость репозитория».
- **Staging.** Одно окружение. Проверка изменений — CI плюс локальная машина.
- **Вынос бэкапов наружу.** Триггер назван выше.
