# Дизайн-система и каркас вёрстки

Как устроена публичная часть сайта: где живут токены, откуда берутся шрифты, из каких компонентов собирается страница и что делать, когда сайт открылся без стилей.

> **Вёрстка страниц ещё не закончена.** Веха 4.1 собрала каркас — шапку, подвал, карточку авто и форму заявки; 4.2 и 4.6 — главную, 4.3 — каталог и карточку автомобиля, 4.4 — автосервис и запчасти, 4.11 — светлые секции и страницы ошибок. «Шоу-рум» и «О компании» приходят вехой 4.5; `/contacts` до неё остаётся заглушкой вехи 4.1 — заголовок, вводный текст из настроек и форма. **Верстать их надо сразу в палитре вехи 4.11** — см. [«Две темы»](#две-темы-тёмная-по-умолчанию-и-светлые-секции).

## Токены

Источник истины — блок `@theme` в [`resources/css/app.css`](../resources/css/app.css). Tailwind v4 конфигурируется в CSS, **файла `tailwind.config.js` в проекте быть не должно**.

Значения перенесены из UI Kit макета (`assets/Макет сайта «ЛАО КАРС»/UI Kit.dc.html`). Сверяться с макетом при вёрстке стоит по смыслу, а значения брать из токенов: оттенок, правленный в одном месте из двух, разъезжается в первый же раз.

Колонка «переключается» — про светлые секции вехи 4.11 (см. [«Две темы»](#две-темы-тёмная-по-умолчанию-и-светлые-секции)): «да» означает, что обёртка `.theme-light` даёт токену другое значение, «нет» — что значение одно на весь сайт.

Полупрозрачных вариантов акцента отдельными токенами нет — подложка 14% и обводка 50% из макета пишутся как `bg-accent-solid/14` и `border-accent/50`. Радиус кнопок и тегов (999px) — штатный `rounded-full`.

**Правила макета, которые токены не выражают:**

- не более двух фоновых оттенков на экране (`page` плюс один из остальных). До вехи 4.11 правило соблюдалось на глаз и нарушалось безнаказанно: все четыре фона были почти чёрными, и третий оттенок было не отличить от второго. На светлом участке он виден сразу — это не регресс, а первый случай, когда правило стало проверяемым;
- один акцентный цвет — для CTA, цен, статуса «в наличии», активных состояний и одного-двух слов в заголовке; большие площади им не заливаются. Разная светлота акцента в тёмной и светлой секции правило не нарушает: оно про цвет, а не про его светлоту на фоне;
- наведение — подъём на 2–6px плюс тень или обводка, `0.2–0.25s`, не больше двух свойств одновременно, без пружинящих easing.

### Границы: три токена вместо одиннадцати прозрачностей

До вехи 4.11 границы писались литералом прямо в разметке — 74 вхождения и **одиннадцать** разных прозрачностей: `/6`, `/7`, `/8`, `/10`, `/15`, `/16`, `/18`, `/20`, `/35`, `/45`, `/70`. Это была не дизайн-система, а дрейф: разница между `/7` и `/8` не видна никому, кроме `git diff`, а одиннадцать вариантов гарантируют, что двенадцатый появится завтра.

Сейчас их три — `line`, `line-strong`, `line-loud`, — и делятся они по РОЛИ, а не по числу: волосок, контрол, выделение. Слить `loud` со `strong` нельзя: бейдж статуса «В пути» и бейдж остальных статусов стоят рядом на одной карточке, и разная яркость обводки — это и есть их различие.

Наведение кнопок хиро (`hover:border-white/70`) переехало на `hover:border-ink-muted`: 70% белого поверх почти чёрного и есть примерно `oklch(0.68)`. Четвёртый токен ради одного наведения был бы тем самым двенадцатым вариантом.

### Почему фоновый токен называется `page`, а не `base`

Пространства имён `--color-*` и `--text-*` в Tailwind v4 порождают один и тот же класс. Токен `--color-base` перебивает штатный размер шрифта `text-base` — `.text-base` начинает красить текст в цвет фона вместо того, чтобы задавать `1rem`. Собирается это без единой ошибки, а вылезает на первом же элементе, которому нужен размер.

То же правило действует для любого нового токена: имя не должно совпадать с ключом другого пространства имён Tailwind.

### Палитра Tailwind по умолчанию обнулена

В `@theme` стоит `--color-*: initial` — классов вида `text-gray-400` или `bg-red-500` в сборке нет вовсе. Случайный оттенок мимо дизайн-системы не доезжает до прода, потому что его просто нет.

Обнуление сделано вехой 4.3, и условие для него было названо заранее: переверстан последний функциональный шаблон (`catalog/index`, `catalog/show` больше не держатся на `text-gray-500`) и заменён вендорный вид пагинации, чьи светлые классы приходили в сборку через `@source`.

**Порядок внутри `@theme` обязателен:**

```css
@theme {
    --color-*: initial;   /* сначала вычистить пространство имён целиком */
    --color-white: #fff;  /* потом вернуть эти два вручную */
    --color-black: #000;

    --color-page: …;      /* и только потом токены макета */
}
```

`--color-*: initial` уносит вместе с серыми и `white` с `black`. До вехи 4.11 на них держалась вся вёрстка проекта — 74 границы вида `border-white/N` плюс подложки `bg-white/N`, — и исчезали эти классы **молча**: сборка зелёная, ошибок нет, просто пропадают все обводки карточек, полей формы и шапки.

**Публичные шаблоны литерал `white` больше не используют вовсе** — границы переехали на токены `--color-line*`, подложки на `--color-overlay`. Это было условием светлой темы, а не уборкой: см. [«Две темы»](#две-темы-тёмная-по-умолчанию-и-светлые-секции).

**Возврат обоих токенов всё равно обязателен.** Вью панели (`resources/views/filament/`) компилируются в `storage/framework/views/`, а эта папка просматривается директивой `@source` — то есть `text-white` и `dark:divide-white/10` оттуда доезжают в публичный бандл. Убрать `--color-white` значит потерять их так же молча, только теперь в панели.

Правило приёмки любой правки этого блока — не «выглядит так же», а поиск в собранном CSS:

```bash
npm run build
grep -o 'border-white' public/build/assets/app-*.css | wc -l   # должно быть больше нуля (панель)
grep -c 'text-gray-' public/build/assets/app-*.css             # должно быть 0
```

Сторож на литерал в **публичных** шаблонах стоит в `tests/Feature/View/PaletteGuardTest.php` и исключает из проверки папку панели и блейдовские комментарии — в последних классы называются по имени в объяснительной прозе.

Панель Filament обнулением не задета — у неё собственная сборка и собственная тема.

## Шрифты

Unbounded (заголовки) и Manrope (текст) **скачиваются на сборке и отдаются со своего домена**. Подключения к `fonts.googleapis.com` в рантайме нет, хотя в HTML-экспорте макета оно есть: внешний CDN на критическом пути рендера — лишний блокирующий запрос к чужому домену и передача IP каждого посетителя третьей стороне.

Конфигурация — блок `fonts` в [`vite.config.js`](../vite.config.js), провайдер `google()` из `laravel-vite-plugin/fonts`. Плагин скачивает woff2, кладёт их в `public/build`, собирает `@font-face`, `<link rel="preload">` и CSS-переменные `--font-unbounded` / `--font-manrope`. В шаблон это приходит директивой `@fonts` в layout — она стоит **до** `@vite`, чтобы preload попал в разбор раньше блокирующего CSS.

Три вещи, которые ломаются молча:

- **`subsets` обязан включать `cyrillic`.** Умолчание провайдера — `['latin']`, а сайт русский целиком. Без кириллического подмножества файл не содержит нужных глифов, браузер уезжает в системный шрифт, а `@font-face` и preload при этом на месте и выглядят рабочими. Проверять надо видом кириллического заголовка, а не наличием запроса за файлом.
- **Ссылка на переменную в `font-family` пишется с запасным именем семейства** — `var(--font-unbounded, 'Unbounded'), sans-serif`. Неопределённая переменная делает всю декларацию невалидной, и страница уезжает в шрифт браузера целиком.
- **`@fonts` при отсутствующем манифесте возвращает пустую строку** и не бросает исключение, в отличие от `@vite`. Тест на preload-ссылку (`LayoutTest`) зелёный только после `npm run build`.

Алиасы намеренно оставлены умолчательными (`unbounded`, `manrope`), а токены названы иначе (`--font-display`, `--font-sans`): иначе одну и ту же переменную на `:root` пишут двое — инлайновый стиль `@fonts` и блок `@theme`, — и кто выиграет, зависит от порядка тегов в `<head>`.

`fontaine` в `devDependencies` стоит ради умолчания `optimizedFallbacks: true`: он считает метрики шрифта и подгоняет под них системный фолбэк, чтобы подмена при `display: swap` не дёргала вёрстку.

## Две темы: тёмная по умолчанию и светлые секции

До вехи 4.11 тема была одна, и в `app.css` это было записано прямым текстом. Заказчик забраковал сплошной тёмный фон, листая живой сайт («слишком много чёрного»), и выбрал по кадрам холодный светлый вариант. Тёмная осталась умолчанием документа, светлая — отдельными секциями.

**Светлая тема НЕ автоматическая и не следует за системой.** `prefers-color-scheme` здесь ни при чём: светлые участки заданы вёрсткой, а не настройкой посетителя.

### Механизм: переопределение токенов, а не замена классов

Класс `.theme-light` вешается на `<section>` (реже — на обёртку с боковыми полями) и переопределяет токены на своём поддереве:

```blade
<section class="theme-light px-5 py-20 lg:px-8 lg:py-30">
    {{-- внутри НИ ОДИН класс не меняется --}}
    <article class="rounded-card border border-line bg-surface p-7">
        <p class="text-ink-muted">Тут `text-ink-muted` тёмный, а `bg-surface` белый.</p>
    </article>
</section>
```

Работает это потому, что Tailwind v4 компилирует `bg-page` в `background-color: var(--color-page)` — утилита ссылается на переменную, а не на значение. Достаточно переопределить переменную на предке.

**Альтернатива — писать светлые варианты классов в каждой секции — отклонена по счёту.** Только границ было 74 штуки, `text-ink-muted` — 65. Она означала бы две параллельные версии каждой карточки, и они разъехались бы на первой же правке: поправят светлую, потому что её видно, и забудут тёмную.

**Цена решения честная: механизм невидим в разметке.** Человек, впервые открывший шаблон светлой секции, не поймёт, почему `text-ink-muted` здесь тёмный. Поэтому он описан здесь, комментарием в самом `app.css` и проверяется `PaletteGuardTest`.

Побочная выгода: переключатель тем, если он когда-нибудь понадобится, ляжет на этот же механизм без переделки.

### Граница механизма: шапка, подвал и хиро остаются тёмными

Класс НЕ вешается на `<body>` и не на layout. Так решил заказчик, и у этого есть вторая, независимая причина: логотип `logo-white.png` белый, и на светлой шапке он бы просто исчез. Модальное окно подтверждения заявки живёт в layout и по той же причине остаётся тёмным на любой странице.

Секция задаёт себе `background-color` и `color` ЯВНО, а не полагается на `bg-*` в разметке: шесть из тринадцати секций главной своего класса фона не имеют вовсе и показывают фон `body`. Без явного фона такая секция осталась бы тёмной, а текст в ней светлым — то есть выглядела бы почти нормально.

Сам блок живёт в `@layer base` намеренно: утилиты Tailwind лежат слоем выше, поэтому `bg-page-alt` на самой секции перебивает здешний `background-color`, и чередование оттенков внутри светлого участка продолжает работать.

### Акцент разделён на чернила и заливку

Это главная ловушка светлой темы, и она молчаливая вдвойне — не роняет сборку и не видна в тёмной теме, где оба токена равны.

- `--color-accent` — **чернила**, и он ПЕРЕКЛЮЧАЕТСЯ. Его читают `text-accent`, `border-accent`, `outline-accent`, `ring-accent` вместе со всеми вариантами `hover:`, `group-hover:`, `peer-checked:`, `aria-pressed:`. `#f9c227` в роли текста на почти белом фоне даёт контраст около **1.4:1** при минимуме 4.5:1 — цена в карточке просто не читается.
- `--color-accent-solid` — **заливка**, и он НЕ переключается. Жёлтая плашка с тёмной надписью одинакова на любом фоне, потому что читаемость там обеспечивается внутри самой плашки, а не её контрастом со страницей.
- `--color-on-accent` — текст ПОВЕРХ заливки, тоже не переключается. До вехи 4.11 эту роль играл `text-page`, и совпадение было случайным: в тёмной теме фон почти чёрный, и надпись читалась.

**Кто напишет `bg-accent` вместо `bg-accent-solid`, получит в светлой секции тёмную заливку под тёмной надписью.** Сборка зелёная, кнопка на месте, читать нечего. Симметричная ошибка — «унифицировать» `--color-on-accent` обратно с `--color-page` — даёт светлую надпись на жёлтом. Оба случая сторожит `PaletteGuardTest`.

`--color-danger` переключается по тому же основанию, что и акцент-чернила: `oklch(0.68 0.19 25)` на почти белом даёт около 3:1, то есть сообщение «поле обязательно» видно хуже, чем подпись к полю, которую оно комментирует.

### `color-scheme` переключается вместе с фоном

`:root { color-scheme: dark }` — не косметика: без него браузер красит нативные контролы по светлой схеме, и выпадающие списки формы заявки («способ связи», «удобное время») отрисуются светлыми. На светлой ОС это выглядит как сломанная форма, а на тёмной проблемы не видно вовсе. Туда же скроллбары и подсветка автозаполнения.

В светлой секции ровно та же поломка наизнанку, поэтому `.theme-light` объявляет `color-scheme: light`. Одна эта строка переключает все десять нативных селектов панели фильтров каталога.

### Где что светлое

| Страница | Светлое | Тёмное |
| :---- | :---- | :---- |
| Главная | полоса доверия, промо, подборка `#cars`, автосервис `#service`, услуги `#services`, отзывы `#about`, преимущества | хиро, быстрый подбор `#selection`, этапы `#process`, прозрачность цены, FAQ, секция заявки |
| Каталог, карточка авто | вся страница | — |
| Автосервис, запчасти, контакты | вся страница, включая секцию заявки | — |
| 404 | содержимое | — |
| 500 | — | вся страница (см. ниже) |
| Шапка, подвал, модалка заявки | — | всегда |

Секция заявки красится по РАСКЛАДКЕ, а не по странице: центрированная карточка (страницы разделов) светлая, двухколоночная на фоновом фото (главная) тёмная. Это одно условие в `x-lead-section` вместо четырёх правок по вызывающим сторонам.

### Приёмка светлой секции

Не «выглядит светло» — это проверяется взглядом и всегда проходит. Проверять надо два утверждения:

1. **правило двух оттенков соблюдено И на стыке с соседней секцией** — то есть смотреть на границу, а не на середину;
2. **нет тёмных полос.** Самая частая причина не класс, а вертикальный внешний отступ: `mb-*` последнего потомка схлопывается наружу через обёртки без `padding` и границы, то есть выпадает из закрашенной области. Отступ в конце светлого участка задаётся `pb-*` на обёртке, а не `mb-*` на её содержимом.

Быстрая проверка полос — в [«Диагностике»](#светлая-секция-с-тёмной-полосой).

### Требование к будущим страницам

**«Шоу-рум» и «О компании» (веха 4.5) верстаются сразу в новой палитре.** Без этой записи их сделают тёмными по образцу соседних шаблонов и переделают потом.

Любой новый блок теперь обязан проверяться в обеих темах, и половина ошибок здесь молчаливые: светлый текст на светлом не роняет сборку.

`@media (prefers-reduced-motion: reduce)` гасит анимации и переходы. Правило заведено вехой 4.1, хотя главный его повод — бегущая строка вехи 4.2: непрерывно ползущий через весь экран текст у человека с вестибулярными нарушениями вызывает тошноту, а выключить его нечем.

## Страницы ошибок

`resources/views/errors/404.blade.php` и `500.blade.php` — веха 4.11. До неё своих шаблонов не было вовсе: на любой опечатке в адресе отдавалась штатная страница Laravel — светлая, без шапки, без логотипа и без единой ссылки обратно. Своего маршрута файлам не нужно, Laravel сам ищет `errors/{статус}.blade.php`.

**404 стоит на общем layout**, с шапкой, подвалом и светлым содержимым: она приходит от работающего приложения. Канонический адрес на ней гасится (`@section('canonical')` пустой), robots — `noindex,follow`.

**500 НЕ стоит на layout, и это главное про неё.** Шапка читает телефон из настроек, подвал — контакты, соцсети и текст гарантии; оба идут в `Setting`, то есть в базу. Пятисотку отдают ровно тогда, когда что-то уже сломано, и «упала база» — самая частая причина. Layout превратил бы одну ошибку в две: исключение внутри шаблона ошибки перехватывать уже нечем, и посетитель получил бы пустой экран.

Что странице можно: `@vite` и `Vite::asset` (чтение манифеста с диска), `route()`, `config()`. Чего нельзя: моделей, `Setting`, кеша, очереди, любых компонентов публичной части. Шапка сведена к логотипу-ссылке, подвала нет.

Сторож — `tests/Feature/Http/ErrorPagesTest.php`: он считает запросы к базе во время отдачи пятисотки и требует ноль. Проверять это чтением шаблона бесполезно — зависимость спрятана в конструкторах компонентов.

Показывается 500 только при `APP_DEBUG=false`; с включённой отладкой на её месте стоит разбор исключения, и это правильно.

| :---- | :---- | :---- |
| `<x-site-header />` | классовый, `App\View\Components\SiteHeader` | `:overlay` — `false` (по умолчанию) липкая шапка с размытием, `true` — прозрачная поверх хиро |

Шапка и подвал **читают настройки сайта сами** — это единственное исключение из правила «Blade не ходит в БД», и оно ограничено этими двумя компонентами. Layout рендерит их на каждой странице, и прокидывание контактов из каждого контроллера означало бы, что забытый контроллер даёт подвал без телефона молча и только на одной странице. Чтение идёт через кеш `Setting`: вся страница стоит один запрос к `site_settings` на холодном кеше и ноль на тёплом, на это стоит сторож в тестах.

**Страницы так не делают.** `ServiceController`, `PartsController` и `ContactController` читают настройки сами и передают в шаблон готовыми.

### Форма заявки: `x-lead-form` и `x-lead-section`

Компонентов два, и граница между ними проходит по `<form>`:

- **`x-lead-form`** — только `<form>` с полями, кнопкой, сообщением об успехе и необязательным заголовком. Собственной обёртки-контейнера у него нет: карточку с фоном, рамкой и отступами рисует вызывающая сторона. Иначе форма несла бы свой фон внутрь чужой карточки — подложка на подложке.
- **`x-lead-section`** — секция-обёртка с двумя раскладками: центрированная карточка (`heading` не задан) и две колонки на фоновом фото (`heading`, `eyebrow`, `text`, `background`). Внутри вызывает `x-lead-form`.

Обычной странице нужен **`x-lead-section`**. Напрямую `x-lead-form` вызывается только там, где форма встраивается в чужую карточку — так сделана заявка в правой колонке карточки автомобиля.

Разделение появилось вехой 4.3 по триггеру, названному вехой 4.2 дословно: третий вызов с раскладкой — повод вынести обёртку. Внутренности `<form>` при этом не изменились ни на строку: там инварианты вехи 3.7 (honeypot за пределами экрана, отсутствие клиентского `page_url`, `old()` во всех полях), и сторож здесь — `LeadStoreTest` с `SectionPagesTest`, обязанные проходить без правок.

**Якорь `#lead-form` живёт на обёртке, а не на самой форме.** На него ведут кнопка «Оставить заявку» в шапке (десктопной и мобильной) и умолчание `home.promo.link_url`, поэтому он обязан быть на странице ровно один — а секция заявки и карточка автомобиля встречаются вместе. В `x-lead-section` он на `<section>`, на карточке авто — на `<div>` с карточкой формы.

**Тему `x-lead-section` выбирает по раскладке, а не по странице** (веха 4.11): центрированная карточка светлая, двухколоночная на фото — тёмная. Это одно условие внутри компонента вместо четырёх правок по вызывающим сторонам, и оно верно по существу: страницы разделов светлые целиком, а фоновый кадр `lead-bg.webp` на главной один и заменить его светлым нельзя. Сама форма при этом инвариантна — она читает токены и работает в обоих окружениях; проверять новое поле надо в обоих, потому что обёртки разные.

### Иконки: `x-ui.icon`

Весь набор — [`resources/views/components/ui/icon.blade.php`](../resources/views/components/ui/icon.blade.php), девять контуров в одном файле.

| Имя | Рисунок | Где стоит |
| :---- | :---- | :---- |
| `wrench` | рожковый ключ | плашка «Автосервис» на главной, блок «ТО и ремонт» прайса |
| `wheel` | колесо в сборе | блок «Шиномонтаж» |
| `sparkle` | пара блёсток | плашка и блок «Детейлинг» |
| `plus-circle` | плюс в круге | блок «Дополнительные сервисы» |
| `gear` | шестерня | плашка «Запчасти» |
| `headset` | гарнитура | плашка «Поддержка» |
| `percent` | процент | кружок промо-баннера |
| `phone` | трубка | кнопка звонка в мобильной шапке |
| `close` | крестик | закрыть мобильное меню |

До вехи с иконками в кружках стояли первые буквы названий («А» — автосервис, «Д» — детейлинг) и символы `%`, `☎`, `✕`. Буква в кружке читается как аватар, а `☎` и `✕` — не рисунок, а глиф шрифта: часть систем подставляет вместо них цветное эмодзи, которое не слушается `text-accent` и не масштабируется вместе с кнопкой.

**Правила набора:**

- сетка 24×24, только контур (`fill="none"`), толщина 1.6, скруглённые концы. Иконка, нарисованная заливкой или в другой толщине, встанет в тот же кружок и будет выглядеть жирнее соседних — при том, что сама по себе нарисована верно;
- **класс размера обязателен на месте вызова**, умолчания у компонента нет намеренно. Класс из `$attributes` не заменяет собственный класс компонента, а дописывается к нему, и порядок двух утилит размера решает CSS, а не порядок слов в атрибуте: `size-5.5` рядом с умолчанием `size-6` дал бы 24px там, где в разметке написано 22px. Ходовые размеры — `size-6` в кружке 48px, `size-5.5` в кружке 40–44px;
- цвет приходит от родителя через `currentColor`: подложка `bg-accent/14` даёт `text-accent`, кружок промо с заливкой `bg-accent` — `text-page`. Поэтому иконки инлайновые, а не `<img>` и не спрайт;
- все значки декоративные: `aria-hidden` стоит внутри компонента и переопределению не подлежит. Смысл несёт соседний текст или `aria-label` на кнопке-родителе;
- неизвестное имя роняет страницу исключением, а не даёт пустой кружок.

**Компонент зовётся `x-ui.icon`, а не `x-icon`, и переименовать его нельзя.** Имя `icon` занято: `blade-ui-kit/blade-icons`, приезжающий зависимостью Filament, регистрирует его классовым компонентом (`blade-icons.components.default`), а зарегистрированное имя старше файла в `resources/views/components/`. `<x-icon>` уезжает в чужой компонент и падает сообщением про файл, которого мы не открывали.

Иконки категорий услуг задаёт `ServiceCategory::icon()`, а не шаблон: плашка экосистемы на главной ведёт в блок категории на `/services`, и значок обязан совпасть с тем, что человек увидит на той стороне.

### Пагинация

Собственный вид — [`resources/views/pagination/catalog.blade.php`](../resources/views/pagination/catalog.blade.php), квадраты 40×40 по макету. Передаётся **именем** в `links('pagination.catalog')`; `Paginator::defaultView()` не используется — подробности и причина в [«Каталоге»](catalog.md).

### Alpine на публичных страницах

Компонент пишется **инлайном в `x-data`**, а не регистрируется через `Alpine.data()` из `@push('scripts')`. Ловушка неочевидная: `@vite` отдаёт `app.js` модулем из `<head>`, модуль исполняется отложенно и сам вызывает `Alpine.start()`. Скрипт, добавленный в конец `<body>` через `@push`, исполнится либо **раньше** модуля (обычный `<script>` — `window.Alpine` ещё нет), либо **позже** (`type="module"` — событие `alpine:init` уже отгремело, а после старта регистрация к разобранной разметке не применяется). Оба варианта ломаются молча: разметка и стили на месте, клики не работают.

Так написаны все три места с Alpine: мобильное меню шапки, авто-сабмит фильтров каталога и фотогалерея карточки. Стек `@stack('scripts')` в layout остаётся — но для скриптов, которым порядок Alpine безразличен.

Атрибуты событий пишутся полной формой (`x-on:click`, `x-on:change`), а не сокращением `@click`: `@` — префикс директив Blade, и сокращение живёт в шаблоне ровно до тех пор, пока имя события не совпало с именем директивы.

### Карточка автомобиля

`x-car-card` используется списком каталога и блоком похожих. В блоке похожих заголовок обязан быть `h3` (`heading="h3"`): иерархия заголовков — не оформление, по ней ходят скринридеры и по ней страницу разбирает поисковик.

Строка характеристик собирается из заполненных полей — пустое значение выпадает целиком, а не оставляет висящий разделитель. Пробег `null` выводится как «Новый»: это не «ноль километров», а автомобиль под заказ, у которого пробега нет вовсе.

Слово «привод» дописывает карточка, а не enum: подпись «Полный» полна в форме админки, где поле уже названо «Привод», и теряет смысл в строке «Электро · Полный · 67 769 км».

## Меню

Состав навигации живёт в [`app/Support/SiteMenu.php`](../app/Support/SiteMenu.php) — **одним списком на шапку и подвал**. Второй список разошёлся бы с первым на первом же новом разделе.

```php
'catalog.index'  => 'Каталог',     // шапка и подвал
'services.index' => 'Автосервис',  // шапка и подвал
'parts.index'    => 'Запчасти',    // шапка и подвал
'contacts.index' => 'Контакты',    // шапка и подвал
'about.index'    => 'О компании',  // только подвал, роут приходит вехой 4.5
```

Состав **намеренно расходится с макетом**: там «Каталог · Услуги · Блог · Контакты». Блог из проекта снят целиком, а его место заняли «Автосервис» и «Запчасти». При сверке вёрстки с макетом меню легко «поправить» обратно — не надо.

**Пункт без зарегистрированного роута выпадает, а не роняет страницу.** Причина не в снисходительности: шапка рендерится на каждой странице, и переименованный роут положил бы весь сайт вместе с формами заявок. Ошибка ловится тестом до мержа (`LayoutTest` проверяет, что все четыре роута зарегистрированы и попали в разметку). Это же закрывает переходный период: «О компании» появится в подвале автоматически, как только веха 4.5 заведёт роут `about.index`.

Активный раздел определяется по **имени роута с маской** (`catalog.*`), а не сравнением адресов: карточка `/catalog/{slug}` обязана подсвечивать «Каталог», и `url()->current()` этого не даёт.

## Как добавить страницу

1. Контроллер в `app/Http/Controllers/`, тонкий: получил данные, отдал в шаблон. Настройки читает он, а не Blade.
2. Роут в `routes/web.php` с именем по конвенции `<раздел>.index`.
3. Шаблон `resources/views/<раздел>/index.blade.php`:

```blade
@extends('layouts.app')

@section('title', 'Заголовок — '.config('app.name'))
@section('description', 'Описание для сниппета, до 160 символов.')

@section('content')
    <x-page-heading eyebrow="Раздел" :title="$title" :intro="$intro" class="theme-light" />

    <section class="theme-light px-5 pt-12 lg:px-8">
        {{-- содержимое --}}
    </section>

    <x-lead-section title="Оставить заявку" />
@endsection
```

Заголовок можно передать слотом, если внутри H1 нужно акцентное слово:

```blade
<x-page-heading eyebrow="Каталог" class="theme-light">
    Автомобили в наличии и <span class="text-accent">под заказ</span>
</x-page-heading>
```

`class="theme-light"` — с вехи 4.11: внутренние страницы светлые целиком, и класс висит на КАЖДОЙ секции отдельно, включая шапку страницы. Не на обёртке вокруг них: у обёртки будут боковые поля страницы, и по краям пойдут тёмные полосы. `x-page-heading` пропускает атрибуты с места вызова до своей `<section>` именно ради этого. Секцию заявки красить не надо — она решает сама, по своей раскладке.

4. Если раздел попадает в меню — добавить его в `SiteMenu`. Пункт появится в шапке и подвале сразу, как только роут зарегистрирован.

Каркас даёт странице: шапку, подвал, `<main id="content">`, skip-link, `@yield('above-header')` под блок выше шапки и `@stack('scripts')` под собственный JS страницы.

## Логотип и favicon

Логотип лежит в `resources/images/logo-white.png` и проходит через манифест Vite (`Vite::asset('resources/images/logo-white.png')`): хеш в имени даёт вечный кеш и корректную инвалидацию при замене. Файл в `public/` пришлось бы сбрасывать у каждого посетителя вручную.

Ассет попадает в манифест благодаря `import.meta.glob(['../images/**'], { eager: true })` в `resources/js/app.js`. **`eager` обязателен**: ленивый вариант из документации Laravel даёт динамические импорты, которые никто не вызывает, и rolldown вырезает их вместе с ассетами — сборка остаётся зелёной, а файла в манифесте нет.

В репозитории лежит веб-копия 440×128 (8,5 КБ). Оригинал 3904×1135 (73 КБ) остался в `assets/Макет сайта «ЛАО КАРС»/`: он рисуется высотой 26–30px, и отдавать 73 КБ ради ста пикселей ширины на каждой странице незачем.

Favicon (`public/favicon.ico`) — знак-ромб из логотипа, 64×64 PNG внутри ICO-контейнера.

## Диагностика

**Сайт открылся без стилей, шрифт системный, вёрстка «рассыпалась».** Не собран фронтенд:

```bash
npm run build     # или `npm run dev` / `composer dev` для разработки
```

`@vite` в этом случае бросает исключение с понятным текстом. Если стили есть, а шрифт всё равно системный — смотрите следующий пункт.

**Стили на месте, но заголовки не в Unbounded.** Манифест шрифтов не собрался, а `@fonts` при его отсутствии молча возвращает пустую строку. Проверить:

```bash
cat public/build/fonts-manifest.json | head -5
```

Файла нет — пересоберите фронтенд. Файл есть, а кириллица всё равно системная — проверьте, что в `vite.config.js` у обоих семейств стоит `subsets: ['latin', 'cyrillic']`.

**Сборка падает или подвисает на скачивании шрифтов.** Плагин ходит на `fonts.googleapis.com` и кеширует результат в `node_modules/.cache/laravel-vite-plugin/fonts`. Повторная сборка в сеть не идёт. В CI под это заведён отдельный шаг `actions/cache` — `actions/setup-node` с `cache: npm` кеширует стор npm, а не этот каталог.

**Шапка без телефона, подвал без адреса.** Не заполнены настройки сайта — админка, «Настройки сайта», вкладки «Контакты» и «Соцсети». В `storage/logs/laravel.log` при этом пишется `WARN [Layout]` с именем незаполненного ключа. Пустая ссылка `tel:` не выводится вовсе: она выглядела бы рабочей.

**Пункт меню пропал.** Роут раздела не зарегистрирован — проверьте `php artisan route:list --except-vendor`. `SiteMenu` выводит только пункты с существующим роутом, поэтому страница не падает, а пункт исчезает.

**Пропали обводки карточек, полей формы и шапки, ошибок нет.** Из `@theme` исчезли `--color-white` и `--color-black` — их уносит `--color-*: initial`, и классы `border-white/8`, `bg-white/6` перестают собираться молча. Проверяется поиском `border-white` в `public/build/assets/app-*.css`.

**Кнопка «Оставить заявку» в шапке скроллит не туда.** На странице два элемента с `id="lead-form"` — якорь ведёт на первый попавшийся. Он живёт на обёртке (`x-lead-section` или карточка формы), и на странице должен быть ровно один: `document.querySelectorAll('#lead-form').length`.

**Alpine-компонент не работает: разметка и стили на месте, клики нет.** Скрипт зарегистрирован через `Alpine.data()` из `@push('scripts')` — так он исполнится либо раньше `app.js`, либо после `alpine:init`. Компонент публичной страницы пишется инлайном в `x-data`.

### Светлая секция с тёмной полосой

Полоса поперёк светлой страницы бывает двух видов, и лечатся они по-разному.

**Целый блок остался тёмным** — на нём просто нет `.theme-light`. Чаще всего это элемент, который не выглядит секцией: строка результатов внутри `<form>`, навигация хлебных крошек, обёртка с боковыми полями.

**Полоса в 10–30 пикселей между двумя светлыми блоками** — вертикальный внешний отступ последнего потомка. Он схлопывается наружу через обёртки без `padding` и границы и выпадает из закрашенной области. Лечится переносом отступа на обёртку: `mb-6` у содержимого → `pb-6` у обёртки с `.theme-light`.

Найти обе разом можно, не разглядывая страницу: скрипт ниже собирает вертикальные диапазоны, в которых ни один элемент `<main>` не рисует светлый фон. Вставить в консоль браузера на светлой странице; пустой массив — чисто.

```js
const cv = document.createElement('canvas'); cv.width = cv.height = 1;
const ctx = cv.getContext('2d', { willReadFrequently: true });
const lum = (c) => {
    ctx.clearRect(0, 0, 1, 1); ctx.fillStyle = c; ctx.fillRect(0, 0, 1, 1);
    const d = ctx.getImageData(0, 0, 1, 1).data;
    return d[3] / 255 < 0.9 ? null : (0.2126 * d[0] + 0.7152 * d[1] + 0.0722 * d[2]) / 255;
};
const main = document.querySelector('main');
const box = main.getBoundingClientRect();
const light = [];
for (const el of [main, ...main.querySelectorAll('*')]) {
    if ((lum(getComputedStyle(el).backgroundColor) ?? 0) < 0.5) continue;
    const r = el.getBoundingClientRect();
    if (r.height >= 1) light.push([r.top + scrollY, r.bottom + scrollY]);
}
light.sort((a, b) => a[0] - b[0]);
const gaps = []; let cur = box.top + scrollY;
for (const [a, b] of light) {
    if (a > cur + 1) gaps.push([Math.round(cur), Math.round(a)]);
    cur = Math.max(cur, b);
}
if (box.bottom + scrollY > cur + 1) gaps.push([Math.round(cur), Math.round(box.bottom + scrollY)]);
console.log(gaps.filter((g) => g[1] - g[0] >= 2));
```

Цвет читается через canvas, а не разбором строки: `getComputedStyle` возвращает токены как `oklch(…)`, и регулярка по `rgb()` их не поймает.

**Тёмный текст на мутном фото.** Маска под подписью рассчитана на тёмную тему: в ней приглушённый СВЕТЛЫЙ текст читается и через полупрозрачный слой, а на светлой тот же процент даёт тёмный текст поверх серого. Непрозрачную часть градиента надо поднять до высоты подписи (`from-page via-page/88 via-30% to-page/8`), а не осветлять текст.
