## Ключевые решения

**Значение хранится одной текстовой колонкой `value`, тип живёт в справочнике.** Альтернативы — типизированные колонки (`value_string` / `value_number` / `value_boolean`) и `jsonb` — отклонены. Типизированные колонки дают три nullable-колонки, из которых две всегда пусты, и ветвление «в какую колонку писать» в модели, фабрике, сиде, редакторе Filament и фильтре каталога — пять мест вместо одного. `jsonb` сохраняет тип сам, но усложняет главный запрос к этой таблице: фильтр каталога — это равенство (`кузов = Седан`), а равенство по `value->>0` требует выражения или GIN даже там, где обычной колонке достаточно `where`. Индексом `value` не покрывается ни в том, ни в другом виде (см. задачу 3) — но плоская колонка оставляет вехе 3.6 свободу добавить индекс, а `jsonb` сразу загоняет в выражение. Числовых **диапазонных** фильтров по динамическим характеристикам не будет: год, цена и пробег — уже колонки `cars` с индексами, а клиренс и число дверей нужны для показа, а не для ползунка. Приведение к типу делается на чтении методами `CarAttributeType`.

**Кеш справочника не заводится.** Соблазн повторить паттерн `Setting::cached()` есть, но выгода мнимая. Карточка авто грузит характеристики через `with('attributeValues.attribute')` — кеш справочника этого запроса не убирает, N+1 решает eager loading. Фильтру каталога справочник нужен один раз на запрос — кеш экономит ровно один запрос к таблице из десятков строк, взамен требуя сброса на событиях модели и ещё одной строки в `tests/Pest.php`, где кеш уже однажды протёк между тестами. Вопрос возвращается в веху 3.6, если профилирование фильтров покажет иное.

**Ключ `key` — машинное имя и публичный контракт.** `body_type`, `color`, `customs_cleared` — `snake_case`, только латиница. По нему в вехе 3.6 строится GET-параметр фильтра (`?attr[body_type]=Седан`), а в 4.3 — обращения из шаблона карточки и микроразметки Vehicle. Подпись (`label`) правится администратором свободно, `key` — нет: его смена ломает сохранённые ссылки на фильтр и код шаблона. Ограничение на формат ставится формой в вехе 3.4; здесь оно фиксируется как правило.

**Допустимые значения `select` — в справочнике, а не `DISTINCT` по колонке.** Тип `select` хранит список вариантов в `options` (`jsonb`). Это ровно то же решение, по которому марка стала отдельной таблицей, а не строкой в `cars`: список для выпадающего фильтра, собранный `DISTINCT`-ом по текстовой колонке, наполняется опечатками наполнителя и плодит фантомные значения — «Кроссовер», «кроссовер» и «Кросовер» как три разных кузова.

**Четыре типа: `text`, `number`, `boolean`, `select`.** Меньше нельзя: «Кузов» — выбор из списка, «Клиренс» — число с единицей, «Растаможен» — флаг, «Комплектация» — свободный текст. Больше (дата, диапазон, ссылка) не нужно ни одной характеристике из известного набора. `unit` осмыслен только для `number` — для остальных типов поле в вехе 3.4 скрывается формой, на уровне БД не запрещается.

**Удаление характеристики из справочника уносит её значения каскадом.** Осиротевшее значение отобразить нечем — нет ни подписи, ни типа, ни единицы, — а восстановление строки справочника не вернёт ему смысла. Подтверждение удаления ставится в админке вехи 3.4. Удаление автомобиля уносит значения тем же каскадом, что и фотографии.

**Одна характеристика — одно значение на автомобиль.** Уникальный индекс `(car_id, car_attribute_id)`. Множественные значения («опции: подогрев руля, панорама, адаптивный круиз») в MVP не нужны и сломали бы и сетку карточки, и фильтр равенства; при необходимости они появятся отдельным типом, а не снятием уникальности.

**Порядок групп в карточке выводится из порядка характеристик.** Отдельной сущности «группа» нет — это строка в справочнике. Позиция группы в сетке = минимальный `sort_order` среди её характеристик. Отдельная таблица групп ради одного поля порядка означала бы третью таблицу и джойн в карточке.

**Кузов и число дверей — две характеристики, а не одна.** Макет пишет «Кузов: Седан, 4 двери» одной строкой. Слитная строка не фильтруется и не типизируется, поэтому в схему ложатся `body_type` (select) и `doors` (number), а сетка вехи 4.3 выводит их отдельными строками. Расхождение с макетом осознанное и в пользу данных.

## Схема данных

| Таблица | Ключевые колонки | Заметки |
| :---- | :---- | :---- |
| `car_attributes` | `key` uniq, `label`, `type`, `unit`, `group`, `options` jsonb, `sort_order`, `show_in_card`, `show_in_filter` | Справочник; `options` заполняется только для `type = select` |
| `car_attribute_values` | `car_id`, `car_attribute_id`, `value` text | uniq `(car_id, car_attribute_id)`; индекс `car_attribute_id` |

Оба внешних ключа покрыты: `car_id` — префиксом уникального индекса, `car_attribute_id` — одиночным (PostgreSQL индекс под FK сам не создаёт — это уже учтено в миграции `cars`). `value` в индексы не входит: лимит записи b-tree в 2704 байта делает индексацию неограниченного `text` миной замедленного действия (см. задачу 3).

Enum `app/Enums/CarAttributeType`: `text`, `number`, `boolean`, `select`.

## Задачи

### Фаза 1 — Тип характеристики и справочник

- [x] **1. Завести enum `CarAttributeType`**
  `app/Enums/CarAttributeType.php`: backed string, cases `Text = 'text'`, `Number = 'number'`, `Boolean = 'boolean'`, `Select = 'select'`. Трейт `App\Enums\Concerns\HasLabels`, метод `label()` — «Текст», «Число», «Да / Нет», «Выбор из списка».
  Дополнительно:
  - `cast(?string $value): string|int|float|bool|null` — приведение хранимой строки к типу. `Number`: строка с точкой → `float`, иначе `int` (иначе «4 двери» выводятся как «4.0»); `Boolean`: `$value === '1'`; `Text` и `Select` — строка как есть; `null` на входе → `null` на выходе.
  - `hasOptions(): bool` — истинно только для `Select`; по нему форма вехи 3.4 показывает редактор списка значений.
  - `hasUnit(): bool` — истинно только для `Number`; единица измерения осмысленна только у чисел.
  Десятичный разделитель — точка. Запятая нормализуется формой на входе (веха 3.4), в БД её быть не должно: `(float) '2,5'` в PHP даёт `2.0` молча.
  Логирование: не требуется, чистый тип без побочных эффектов.
  Проверка: `php artisan tinker` — `App\Enums\CarAttributeType::Number->cast('190')` возвращает `int(190)`, `->cast('2.5')` возвращает `float(2.5)`, `CarAttributeType::Boolean->cast('0')` возвращает `false`.

- [x] **2. Справочник характеристик: миграция, модель, фабрика** *(зависит от 1)*
  Миграция `create_car_attributes_table`: `id`, `key` (string, unique), `label` (string), `type` (string), `unit` (string nullable), `group` (string nullable), `options` (`jsonb` nullable), `sort_order` (`unsignedSmallInteger`, default 0), `show_in_card` (boolean, default **true**), `show_in_filter` (boolean, default **false**), `timestamps`. Других индексов нет: справочник — десятки строк, читается целиком.
  Значения по умолчанию выбраны по частоте: характеристику заводят, чтобы показать её в карточке, а в фильтр попадают единицы.
  `app/Models/CarAttribute.php` в стиле проекта (`final`, `declare(strict_types=1)`, `#[Fillable([...])]`, `HasFactory`): касты `type => CarAttributeType::class`, `options => 'array'`, `sort_order => 'integer'`, `show_in_card => 'boolean'`, `show_in_filter => 'boolean'`. `#[RouteKey]` не ставится — справочник в публичный URL не выходит.
  Связь `values(): HasMany` на `CarAttributeValue`. Скоупы через `#[Scope]`: `inCard()`, `inFilter()`, `ordered()` (по `sort_order`, затем `label`).
  Методы: `cast(?string $value): mixed` — делегирует в `$this->type->cast()`; `format(?string $value): ?string` — приводит и готовит строку для вывода: `Boolean` → «Да» / «Нет», `Number` с `unit` → «190 мм», `null` → `null`; `isValidValue(string $value): bool` — для `Select` проверяет вхождение в `options`, для прочих типов истинно. Подписи «Да» / «Нет» живут здесь и больше нигде — это то же правило, по которому подписи enum-ов живут в `label()`.
  `database/factories/CarAttributeFactory.php`: `key` — `fake()->unique()`-производный `snake_case` (unique-индекс), `type` по умолчанию `Text`. Состояния: `text()`, `number(?string $unit = null)`, `boolean()`, `select(array $options)`, `inFilter()`, `hiddenInCard()`, `inGroup(string $group)`.
  Логирование: не требуется — слой данных.
  Проверка: `php artisan migrate`; в tinker `CarAttribute::factory()->number('мм')->create(['label' => 'Клиренс'])->format('190')` возвращает «190 мм»; `->boolean()->create()->format('1')` возвращает «Да».

### Фаза 2 — Значения и чтение из карточки автомобиля

- [x] **3. Значения характеристик: миграция, модель, фабрика** *(зависит от 2)*
  Миграция `create_car_attribute_values_table`: `id`, `car_id` (`constrained()->cascadeOnDelete()`), `car_attribute_id` (`constrained()->cascadeOnDelete()`), `value` (`text`), `timestamps`.
  Индексы: `unique(['car_id', 'car_attribute_id'])` — одна характеристика на автомобиль имеет ровно одно значение; `index('car_attribute_id')` — покрытие внешнего ключа (PostgreSQL не создаёт его сам) и вход для фильтра каталога вехи 3.6. Порядок колонок в уникальном индексе значим: он покрывает выборку «все характеристики авто» префиксом `car_id`. Третьего индекса не нужно.
  `value` — `text`, а не `string`: свободная «Комплектация» может быть длиннее 255 символов, а в PostgreSQL `text` и `varchar` по производительности не различаются.
  **`value` в индекс не входит осознанно.** Составной `(car_attribute_id, value)` напрашивается под равенство фильтра, но запись b-tree в PostgreSQL ограничена 2704 байтами: кириллица — 2 байта на символ, то есть 1352 символа комплектации, вставленных заказчиком копипастом, роняют `INSERT` ошибкой `index row size ... exceeds btree version 4 maximum 2704`. Свалится это не на демо-данных, а на реальном контенте. Равенство по `value` доотсеивается по узкой выборке: характеристика — это десятки строк справочника на несколько тысяч авто. Составной индекс подбирается в вехе 3.6 вместе с остальным тюнингом фильтра, и любой индекс по `value` обязан ограничивать длину выражением (`left(value, N)`) — иначе упрётся в тот же лимит.
  `app/Models/CarAttributeValue.php`: `#[Fillable(['car_id', 'car_attribute_id', 'value'])]`, связи `car(): BelongsTo` и `attribute(): BelongsTo` (внешний ключ `car_attribute_id`, класс `CarAttribute`). Аксессоры `casted` (типизированное значение) и `formatted` (готовая строка) — оба делегируют в `$this->attribute`. В PHPDoc обоих аксессоров явно записать, что они обращаются к связи `attribute` и в списках требуют `with('attributeValues.attribute')`: без этого каждая строка сетки характеристик даёт отдельный запрос — ровно тот N+1, что перечислен антипаттерном в `ARCHITECTURE.md`.
  `database/factories/CarAttributeValueFactory.php`: `car_id` через `Car::factory()`, `car_attribute_id` через `CarAttribute::factory()`, `value` — строка. Состояние `forAttribute(CarAttribute $attribute, string $value)`.
  Логирование: не требуется — слой данных.
  Проверка: `php artisan migrate`; в tinker повторная вставка той же пары `(car_id, car_attribute_id)` падает на уникальном индексе; удаление автомобиля и удаление характеристики уносят значения.

- [x] **4. Подключить характеристики к модели `Car`** *(зависит от 3)*
  В `app/Models/Car.php` добавить:
  - `attributeValues(): HasMany` на `CarAttributeValue`.
  - `cardAttributes(): Collection` — характеристики для сетки карточки: берёт `$this->attributeValues`, отбрасывает те, у чьей характеристики `show_in_card = false`, сортирует по `attribute.sort_order`, группирует по `attribute.group`. Метод работает поверх **уже загруженной** коллекции и сам запросов не делает; порядок групп определяется минимальным `sort_order` внутри группы. Контроллер карточки (веха 4.3) обязан грузить `with('attributeValues.attribute')`.
    Характеристики без группы собираются под ключом `null` и идут последними. Ключ фиксируется явно, потому что `Collection::groupBy()` по `null` отдаёт `''`, и `@foreach ($groups as $group => $items)` в вехе 4.3 нарисует секцию с пустым `<h3>`; шаблон 4.3 выводит эту группу блоком без заголовка.
  - `attributeValue(string $key): mixed` — типизированное значение по машинному ключу или `null`. Нужен вехе 4.3 точечно: микроразметке Vehicle нужен `bodyType`, а не вся сетка.
  - `syncAttributeValues(array $values): void` — принимает `['body_type' => 'Седан', 'doors' => '4']`, пишет через `updateOrCreate` по паре. Метод используют редактор вехи 3.4 и сид задачи 6 — единственный путь записи, чтобы правила ниже не разъехались по двум реализациям. Три правила задаются здесь и нигде больше:
    - **Резолв ключа — одним запросом на вызов.** Справочник берётся целиком: `CarAttribute::query()->get()->keyBy('key')`, дальше цикл идёт по памяти; по этой же карте отбрасываются ключи, которых в справочнике нет. Поиск `where('key', $key)->first()` внутри цикла — это 9 запросов на автомобиль, в сиде задачи 6 — 108 лишних, а в редакторе 3.4 — запрос на каждое поле формы при сохранении. Ровно этот антипаттерн перечислен в `ARCHITECTURE.md` и ровно его чинил коммит `18fa20f` в сиде фотографий.
    - **Нормализация до проверки на пустоту.** Значение сначала приводится к строке по типу характеристики (`bool` → `'1'` / `'0'`, число → строка без локали, разделитель — точка), и только потом проверяется — **строго**: `$value === null || $value === ''`. Ни `empty()`, ни неявная ложность: `empty('0')` в PHP истинно, и «Растаможен: Нет» (одна из девяти характеристик стартового набора и одна из пяти фильтруемых) была бы удалена вместо сохранения — характеристика пропала бы из сетки, а фильтр вехи 3.6 не нашёл бы ни одного нерастаможенного авто. Явная нормализация закрывает и второй вопрос: во что PDO превращает PHP-булево при биндинге в `text`-колонку, зависит от драйвера и на усмотрение реализации оставаться не должно.
    - **Пустое значение удаляет запись** — администратор очистил поле, характеристика уходит из карточки, а не остаётся пустой строкой.
    - **Значение проверяется через `$attribute->isValidValue($value)`.** Не прошедшее проверку не пишется и логируется предупреждением с `key` и значением. Аргумент про единственный путь записи применим к списку `options` ровно так же, как к правилу «пусто = удалить»: редактор вехи 3.4, а позже любой импорт, запишут «Кроссовeр» с латинской `e`, и в фильтре появится вариант, по которому ничего не находится.

  Логирование: WARNING на отброшенном значении (`key` и значение) — единственное исключение из «слой данных не логируется»: значение, не прошедшее `isValidValue()`, исчезает молча, и без записи в лог разбираться будет не с чем.

## Риски

| Риск | Как проявится | Что делать |
| :---- | :---- | :---- |
| N+1 на сетке характеристик | Карточка с 9 характеристиками даёт 10 запросов; в списке каталога — умножается на число карточек | Аксессоры документированы как требующие `with('attributeValues.attribute')`, отдельный тест на количество запросов (задачи 3, 7) |
| Значение `select` вне `options` | Фильтр каталога вехи 3.6 показывает вариант, по которому ничего не находится | `isValidValue()` вызывается на единственном пути записи `syncAttributeValues()` — не прошедшее не пишется и логируется; плюс проверка значений сида тестом (задачи 2, 4, 6, 7) |
| Булево «Нет» принято за пустое значение | Администратор снимает «Растаможен», запись удаляется вместо `'0'` — характеристика пропадает из карточки, фильтр 3.6 не находит нерастаможенных авто | Нормализация в строку до проверки, строгое сравнение `=== null \|\| === ''` вместо `empty()`, тест на круговой рейс `false` → `'0'` → «Нет» (задачи 4, 7) |
| Длинное значение в индексе по `value` | `INSERT` падает с `index row size ... exceeds btree version 4 maximum 2704` на реальной комплектации от заказчика (кириллица — 2 байта на символ, хватает 1352 символов) | `value` в индексы не входит; составной индекс под равенство подбирается в вехе 3.6 и только с ограничением длины через `left(value, N)` (задача 3) |
| N+1 на резолве ключа характеристики | Сохранение формы 3.4 даёт запрос на каждое поле, сид задачи 6 — 108 лишних запросов | Справочник читается одним запросом на вызов `syncAttributeValues()`, сид вызывает метод один раз на автомобиль; тест на число запросов (задачи 4, 6, 7) |
| Смена `key` после запуска | Ломаются сохранённые ссылки на фильтр и обращения из шаблонов карточки | `key` зафиксирован как публичный контракт в `AGENTS.md`; правится подпись, а не ключ (задача 8) |
| Число приводится к `float` там, где нужен `int` | В карточке «4.0 двери» вместо «4 двери» | Приведение по наличию точки в строке, тест на оба случая (задачи 1, 7) |
| Десятичная запятая в значении | `(float) '2,5'` молча даёт `2.0` — клиренс превращается в мусор | Разделитель — точка, нормализация запятой на входе формы вехи 3.4; правило записано в задаче 1 |
| Каскад при удалении характеристики | Администратор удаляет «Кузов» и молча теряет значения на всех автомобилях | Каскад осознан (осиротевшее значение нечем отобразить), подтверждение удаления ставится в админке вехи 3.4 |
| Дубли значений на автомобиле | Две записи «Кузов» на одной карточке, сетка показывает обе | Уникальный индекс `(car_id, car_attribute_id)`, тест на повторную вставку (задачи 3, 7) |
| Пустая строка вместо удаления | Администратор очистил поле, а в карточке остаётся пустая строка характеристики | `syncAttributeValues()` удаляет записи с пустым значением (строго `null` или `''` после нормализации) — единственный путь записи (задача 4) |
| Случайные значения в сиде | Повторный `db:seed` переписывает демо-каталог, диффы становятся шумом | Значения заданы константой, без `fake()` (задача 6) |
| Кеш справочника заведён «на всякий случай» | Ещё один источник протечки между тестами, как уже было с настройками | Кеш не заводится; вопрос возвращается в веху 3.6 по результатам профилирования |
| Авто без характеристик не предусмотрено | Сетка карточки падает или рисует пустой блок на реальном каталоге | Один автомобиль в сиде намеренно без характеристик, тест на пустую коллекцию (задачи 6, 7) |
